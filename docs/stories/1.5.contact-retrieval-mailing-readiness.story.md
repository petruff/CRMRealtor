## Story

**As a** realtor managing 200–500 people with occasional help from an assistant,  
**I want** to find the right contact quickly and know which records are actually ready for physical mail,  
**so that** daily calls, texts, emails, and postcard campaigns remain trustworthy as the database grows.

**Traceability:** The realtor expects 200–500 contacts, works mainly from a laptop with occasional phone lookup, primarily calls/texts/DMs, and requires a per-contact physical-mail checklist and date. The live requirements audit found no retrieval control on `/contacts` and found contacts without deliverable addresses counted and checkable in `/mailers`. [Source: `docs/prd/realtor-requirements-coverage.md#requirement-coverage`; `docs/prd/realtor-requirements-coverage.md#browser-observations`]

**Dependency:** Story 1.4 is Done and provides persistent campaign/send storage, CLI mailer operations, owner-scoped repositories, server actions, and the Apple-inspired responsive workspace.

## Acceptance Criteria

1. **CLI-first contact retrieval.** A UI-independent contact-query function and CLI find contacts by a bounded, case-insensitive query across displayed/preferred name, email, phone, city, postal code, and tags, with an optional Hot/Warm/Nurture filter. Results preserve Hot → Warm → Nurture ordering, emit stable JSON, reject unknown/malformed arguments with a non-zero exit, and do not import a React or browser module.
2. **Fast contacts search and filtering.** `/contacts` exposes a semantic GET search form with an explicit label, lead-type filter, result count, clear control, and useful empty state. The URL reflects the active query/filter, reload retains it, and grouped results remain Hot → Warm → Nurture without hiding empty-search context.
3. **Complete quick-action set.** Every contact row exposes Call and Text when a phone exists and Email when an email exists. Actions use contact-specific accessible names, at least 44×44px targets, no empty `tel:`, `sms:`, or `mailto:` link, and do not replace the contact-detail path.
4. **Shared mailing-readiness rule.** A pure domain rule considers a contact eligible for physical mail only when street address, city, state, and postal code are all non-blank. The rule is shared by summary calculation, server mutation validation, CLI behavior, and UI; it is not duplicated in React.
5. **Truthful campaign summaries and rows.** Campaign sent/remaining/total counts include only currently mail-ready contacts. Contacts needing an address are visibly separated or identified, display the missing fields and an Edit contact path, and cannot be newly marked sent. The UI never counts an incomplete address as a deliverable postcard.
6. **Historical safety and race protection.** Existing send history is never deleted merely because a contact later loses address data. A historical date remains visible with an address warning and may be cleared, but a new mark is rejected. The server re-reads the contact and rechecks eligibility immediately before persistence so stale UI cannot create a false success.
7. **Honest integration copy.** `/connections` no longer claims that Gmail needs no lengthy Google review or that Calendar needs nothing extra to set up. Copy states that scopes, multi-user use with the assistant, provider verification, and production configuration must be confirmed before availability.
8. **Apple-inspired responsive and accessible experience.** The updated routes reuse the existing `--sk-*` system, system typography, calm hierarchy, visible focus, reduced-motion behavior, light/dark themes, native controls, and a usable 390px layout with no horizontal overflow.
9. **Regression protection.** Focused tests cover query normalization/filtering/order/bounds, mailing eligibility, summary math, historical sends, command-side race validation, and failure handling. Lint, typecheck, the full test suite, both CLI smokes, optimized build, and desktop/390px runtime review pass.

## Dev Notes

### Product and Evidence Boundaries

- This story closes the first implementable gaps from the realtor questionnaire; it does not equate local feature completeness with production readiness. [Source: `docs/prd/realtor-requirements-coverage.md#recommended-delivery-sequence`]
- At the audited scale of 200–500 contacts, deterministic in-process filtering is proportionate. A search service, cache, or fuzzy-search dependency is not authorized.
- Physical-mail eligibility is a data-integrity boundary. The UI may explain and guide, but the server command must be authoritative.
- The current live repository is not configured in this workspace. Demo/live disclosure must remain honest and CLI live mode must refuse missing credentials rather than fall back silently.

### Architecture Boundaries

- Reuse Next.js 15 App Router, TypeScript, Tailwind CSS v4 tokens, Supabase/Postgres, and the typed repository/application boundaries. React must not reproduce query or eligibility rules.
- `/contacts` should use URL GET parameters and server rendering; no client state manager is needed. Normalize unexpected values safely and do not trust query-string types.
- `markMailerSentCommand` currently receives only a mailer repository. Evolve it to receive the contact repository as an explicit validation dependency, and update every action/CLI/test call site.
- Preserve the existing mailer storage model. Ineligibility affects current deliverability and new marks, not deletion of historical `mailer_sends` rows.
- Expected paths include `packages/crm/lib/application/contact-query.ts`, adjacent tests, `packages/crm/scripts/search-contacts.ts`, `packages/crm/app/contacts/page.tsx`, `packages/crm/lib/domain/mailer.ts`, `packages/crm/lib/application/mailer-commands.ts`, `packages/crm/components/mailer-workspace.tsx`, `packages/crm/app/connections/page.tsx`, and supporting docs/tests.

### UX and Accessibility Boundaries

- Preserve the approved Apple-inspired design system; improve retrieval and integrity without removing routes, screens, menus, or existing capabilities.
- Search must work by keyboard and remain useful without JavaScript. Controls and result feedback require programmatic labels; icon actions need contact-specific names.
- On mobile, do not turn each contact into a dense desktop table. Maintain the current stacked/grouped cards and bottom-navigation containment.
- In mailers, make “needs address” explanatory rather than punitive. Provide a direct Edit path and keep historical state understandable.

### Testing

- Query cases: whitespace/case/diacritics-safe normalization, preferred versus legal name, phone/email/city/postal/tags, optional lead type, stable order, no-match, empty query, and input/argument bounds.
- Mailer cases: complete address, each missing component, whitespace-only fields, eligible summary, duplicate/historical sends, missing contact, stale UI/address removed before mutation, safe unmark, and repository failure.
- Runtime path: search → filter → reload → clear → no-match; campaign summary → incomplete row cannot mark → edit path → eligible mark; desktop and 390px in both themes.
