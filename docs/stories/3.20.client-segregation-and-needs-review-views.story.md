# Story 3.20 — Client Segregation & Needs Review Views

**Epic:** 3 — CRM operating foundation

## Story

**As Judith, the realtor organizing the contacts she is actively working,**  
**I want** clear Leads, Clients, Needs review and All contacts views, with current and past clients separated inside Clients,  
**so that** clients no longer disappear inside the main working list and I can find each relationship group without changing its follow-up priority or source history.

**Traceability:** Judith audio feedback relayed on 2026-08-18; Story 3.19 qualification boundary; existing `relationship`, contact query and Smart List contracts.

**Dependencies:** Stories 3.1, 3.2, 3.7 and the implemented Story 3.19 domain contract. Story 3.19 remains the authority for `qualified | needs-qualification`, Hot/Warm/Nurture invariants and explicit import mapping.

## Acceptance Criteria

1. Active Contacts exposes button-style views `Leads`, `Clients`, `Needs review` and `All contacts`; `/contacts` defaults to `Leads`, which excludes `active-client` and `past-client`, while `All contacts` restores every non-archived contact.
2. `Clients` contains exactly `active-client` plus `past-client` contacts and exposes accessible subtabs `All clients`, `Active clients` and `Past clients`; the parent Clients control remains selected for every client subview.
3. `Needs review` is the only new user-facing name for records whose internal qualification value is `needs-qualification`. No database, API, import/export or command value is renamed, and `Hot`, `Warm` and `Nurture` remain the only lead-temperature values.
4. One deterministic, bounded contact-scope query contract is implemented CLI/application-first and is reused by the Contacts route. It supports `leads`, `clients`, `active-clients`, `past-clients`, `needs-review` and `all`, rejects invalid scope values in CLI/application use, and maps a missing web scope to `leads`.
5. Search, `leadType`, active Smart List and the selected contact scope compose as an intersection. Switching primary views or client subtabs preserves valid search, temperature and Smart List query parameters; clearing one filter does not silently clear the others.
6. Existing links using `qualification=needs-qualification` remain compatible and resolve to the same records as `Needs review`; generated UI links use the canonical scope contract and never expose a new stored qualification value.
7. Archived contacts remain a separate, explicitly selected read-only view. Active contact scopes never include archived records, and entering or leaving Archived cannot silently reinterpret an active scope as archived data.
8. Each primary view and client subview displays truthful result counts, a scope-specific title and a useful empty state. Search/no-result messaging names the active scope and offers a clear action that preserves unrelated valid filters where appropriate.
9. Navigation is operable with keyboard and screen reader, uses semantic navigation plus `aria-current`, has visible focus and selected states, and remains usable without horizontal overflow at 390 px and desktop widths. Controls do not depend on color alone and respect reduced-motion preferences.
10. Import continues to set `relationship` only from an explicit supported column/mapping. Generic vendor `Status` or `Rating` remains source provenance and must not infer `lead`, `active-client`, `past-client`, `sphere` or qualification; uncertain records may be deliberately mapped to `needs-qualification` only through the existing explicit contract.
11. Existing relationship, qualification, lead-temperature, cadence, pipeline, Mailchimp, duplicate resolution, Smart List persistence and contact quick actions remain unchanged. This story requires no new contact table, duplicate dashboard silo or schema migration.
12. Focused domain/application/CLI/UI/import regressions pass, followed by `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` from `packages/crm`.

## Out of Scope

- Adding `Client` or `Needs review` as a lead temperature, pipeline stage or Mailchimp tag.
- Guessing relationship from generic source status/rating values or bulk-reclassifying imported contacts.
- Removing `sphere` contacts from the default non-client working view; `Leads` is the user-facing name for the non-client working scope (`lead` plus `sphere`).
- Changing archive lifecycle, permanent deletion, relationship schema or contact persistence.
- Deploying Story 3.19 or importing Judith's production file.

## Dev Notes

### Domain boundaries

- `leadType` and `relationship` are orthogonal. A client may remain Hot, Warm or Nurture; this story changes retrieval/presentation only. `relationship` already allows `lead | active-client | past-client | sphere`. [Source: `packages/crm/lib/domain/contact.ts#domain-model`]
- Story 3.19 owns `qualified | needs-qualification`; only the UI copy changes from `Figure out` to `Needs review`. Import/export/API/SQL values remain stable. [Source: `docs/stories/3.19.judith-workflow-controls-and-claude-routing.story.md#acceptance-criteria`]
- The default `Leads` scope means non-client working contacts (`lead` and `sphere`) because Judith asked to remove clients from the main list, not to hide sphere contacts. `All contacts` is the lossless active-record view.

### Query and Smart List composition

- Extend the existing deterministic `queryContacts` application seam rather than filtering only in JSX. It is already shared by CLI and the server-rendered route and currently composes bounded text search with lead type. [Source: `packages/crm/lib/application/contact-query.ts#shared-deterministic-query`]
- Smart Lists already support `relationship` criteria and cap results at 500. Do not create duplicate system records merely to represent the new navigation; apply the selected scope as an additional intersection over the canonical contact source. [Source: `packages/crm/lib/domain/smart-list.ts#smart-list-definition-v1`; `docs/prd/omnix-crm-parity-roadmap.md#explicit-non-targets`]
- The current Contacts route applies Smart List, text/temperature query and qualification in separate steps and loses some parameters when links are rebuilt. Consolidate parameter preservation around the canonical active scope. [Source: `packages/crm/app/contacts/page.tsx#contacts-page`]

### Import and lifecycle safety

- Story 3.19 requires generic source `Status`/`Rating` to remain provenance unless deliberately mapped. This story must not use those values to populate the Clients view. [Source: `docs/stories/3.19.judith-workflow-controls-and-claude-routing.story.md#acceptance-criteria`]
- Matching order remains external platform ID, normalized email, then normalized phone; no view may create or merge records. [Source: `packages/crm/docs/contact-imports.md#safety-model`]
- Archived contacts remain reversible and separate from active retrieval. [Source: `packages/crm/docs/rich-contact-operations.md#operational-boundaries`]

### Architecture and project structure

- Implement in the existing Next.js 15 App Router/TypeScript application, using URL state and Tailwind v4; no new state manager, ORM or component library. [Source: `docs/architecture/tech-stack.md#decision`]
- Relevant implementation seams: `packages/crm/lib/application/contact-query.ts`, `packages/crm/scripts/search-contacts.ts`, `packages/crm/app/contacts/page.tsx`, contact form/detail surfaces, Smart List controls and their colocated tests.
- `docs/accumulated-context.md` and `.aexos/gotchas.json` are absent. Cross-story coherence is therefore derived from Stories 3.1, 3.2, 3.7, 3.19, the active roadmap and current source; do not infer additional requirements from missing artifacts. [Source: `docs/prd/omnix-crm-parity-roadmap.md#autonomous-decisions`]
