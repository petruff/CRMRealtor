## Story

**As Judith,**
**I want** contact imports and everyday service connections to complete with truthful, recoverable guidance,
**so that** I can trust Omnix without interpreting database receipts, provider scopes, or developer-only failures.

**Incident traceability:** On 2026-08-23 Production parsed and applied all 144 rows from Judith's Apple Numbers workbook, reporting 117 created, 27 updated, zero unchanged, and zero failed, then displayed “Import completed but its immutable receipt could not be recorded.” Production reconciliation subsequently showed 308 active contacts, zero exact canonical email/phone duplicate groups, and pipeline totals of 190 New, 6 Contacted, 55 Active, 8 Closed, and 49 Lost. The source of the receipt failure is a stale `data_import_runs.format` constraint that allows CSV/vCard/Excel/JSON but not the already supported `numbers` format. [Source: Production logs and authenticated read-only reconciliation, 2026-08-23; `packages/crm/app/import-actions.ts`; `packages/crm/supabase/migrations/0023_data_portability_operational_api.sql`]

**Connector traceability:** Production contains an active Mailchimp connection and selected audience, but its Marketing API audience read returns a forbidden classification after successful OAuth callbacks. The provider client uses the metadata-specific `OAuth` authorization scheme for Marketing API requests even though current Mailchimp Marketing API guidance specifies Bearer authentication. Google remains `authorizing` with no granted operational scopes after a failed callback; the UI incorrectly describes the expected pre-consent state as unavailable capability health, while the callback suppresses the diagnostic stage/category. The Google implementation also rejects the entire aggregate authorization if Judith grants only a subset, contrary to the existing independent capability model. [Source: Production logs and authenticated Connections page, 2026-08-23; `packages/crm/lib/providers/mailchimp-client.ts`; `packages/crm/lib/providers/google-client.ts`; `packages/crm/app/connections/page.tsx`; `docs/stories/4.2.google-email-calendar-operations.story.md#acceptance-criteria`]

## Acceptance Criteria

1. **Numbers receipts are valid.** A forward migration expands the governed import format contract to include `numbers`, preserves every existing immutable receipt, and includes pgTAP coverage for a Numbers receipt plus divergent replay rejection.
2. **Receipt compatibility is checked before mutation.** The signed-in server action performs an authenticated database contract preflight after parsing/preview and before the first contact mutation. Missing migration, unsupported format, invalid authority, or incompatible idempotency fails with user-safe developer guidance and writes no contact.
3. **The incident is recoverable without duplicates.** Replaying the exact workbook after the migration uses existing atomic row receipts, performs no duplicate contact/note/activity mutations, reconstructs the original created/updated/unchanged row outcomes, and records the missing immutable import run with the same file-bound idempotency key.
4. **Unexpected receipt failure remains truthful and actionable.** Safe structured telemetry records stage, format, aggregate counts, Supabase error category/code, and a correlation reference without PII, raw rows, file bytes, access tokens, OAuth codes, or provider bodies. The user sees that contacts are safe and that Omnix can recover the audit record; the completed import is not mislabeled as wholly failed.
5. **Mailchimp uses the current provider contract.** Mailchimp OAuth metadata continues to use its documented `OAuth` header, while Marketing API requests use Bearer authentication. Tests prove both boundaries and never expose the token. The existing active connection can list audiences without requiring another OAuth cycle when the stored token is valid.
6. **Mailchimp setup is one guided owner action.** The page distinguishes account authorization, audience selection, initial baseline, signed webhook, and reconciliation. “Finish Mailchimp setup” executes or resumes only the missing idempotent steps, reports provider or developer blocks specifically, and does not claim synchronization before baseline and webhook receipts exist.
7. **Google pending state is not reported as broken health.** An `authorizing` connection with no granted scopes is presented as an expected, owner-actionable consent step. Capability health is labeled unavailable only when an active connection fails its persisted capability read.
8. **Google partial consent is preserved.** The aggregate owner authorization may persist the subset of requested Gmail/Calendar operational scopes actually granted, provided identity authority and at least one requested operational scope are valid. Each capability remains independently active or missing; denied capabilities stay disabled and the UI offers one guided retry for only the remaining permission set.
9. **OAuth failures are diagnosable without secrets.** Google and Mailchimp connect/callback routes log a fixed schema with provider, operation, stage, safe error category, and correlation/support reference. User notices distinguish cancellation/denial, expired browser transaction, deployment configuration, incomplete permissions, and developer-side persistence failures.
10. **Provider authority remains external.** No test or developer account substitutes for Judith's consent. Production is not labeled Google- or Mailchimp-live until provider authorization, one safe operation, baseline/webhook where applicable, receipt, disconnect/revoke, and real-account UAT are evidenced.
11. **Regression and release proof.** Focused application/provider/UI tests, clean migration replay, rollback rehearsal, lint, typecheck, full test suite, optimized build, authenticated 390/768/1440 smoke checks, import recovery, and redacted connector health checks pass before Production promotion.

## Out of Scope

- Reading Gmail message bodies or attachments, broad primary-calendar access, autonomous outbound communication, or bypassing Google verification.
- Replacing Mailchimp unsubscribe authority, silently creating a new audience, or sending a newsletter during recovery.
- Fuzzy name-only contact merging, destructive deletion, or bulk reclassification beyond the source-file result already reconciled.

## Dev Notes

- Imports remain bounded, hashed, previewed, and discarded; only mapping metadata and aggregate/row receipts persist. [Source: `docs/architecture/data-portability-operational-api.md#2-approved-extension`]
- Import finalization and receipt append use narrow workspace-bound RPCs; broad service-role contact CRUD is prohibited. [Source: `docs/architecture/data-portability-operational-api.md#8-api-and-command-model`]
- Operational evidence is retained after Production use; rollback disables new entry points and must not erase existing receipts. [Source: `docs/architecture/data-portability-operational-api.md#12-rollout-rollback-and-support`]
- Connector authorization is separate from Google sign-in, and every provider remains bounded by exact workspace, account, scope, secret, receipt, and revocation authority. [Source: `docs/architecture/connector-security-jobs-approvals.md#data-flow-connector-oauth-and-account-binding`]
- Provider calls do not hold database transactions open; completion uses persisted authority and must remain replay-safe. [Source: `docs/architecture/connector-security-jobs-approvals.md#performance-capacity-and-cost`]
- Logs are redacted operational telemetry and never replace durable receipts. [Source: `docs/architecture/connector-security-jobs-approvals.md#observability`]
- Google missing or denied scopes disable only dependent capabilities. The aggregate owner screen may request the three reviewed operational scopes, but persisted capability rows remain independent. [Source: `docs/stories/4.2.google-email-calendar-operations.story.md#acceptance-criteria`]
- Current Mailchimp primary guidance uses the `OAuth` scheme for OAuth metadata and Bearer authentication for Marketing API requests. [Source: Mailchimp OAuth 2 and Marketing API Fundamentals documentation, reviewed 2026-08-23]
- ClickUp synchronization and the configured story template/checklist files are unavailable in this session; this incident story is tracked locally using the established repository story format.
