## Story

**As a** solo real estate agent,  
**I want** named physical-mail campaigns with a persistent per-contact checklist and automatic send dates,  
**so that** I can see exactly which clients received each postcard and when without maintaining a separate spreadsheet.

**Traceability:** Phase 1 explicitly includes a “Mailer checklist — named mailers, per-contact checkbox, auto-date.” The client described physical mailings, not email campaigns: “a checkbox for each that I can check off and it dates it. I just want to know what was sent, when, and if it was done.” [Source: `docs/prd/requirements-analysis-v2.md#2-blockers-resolved`; `docs/prd/requirements-analysis-v2.md#phase-1--the-thing-shes-missing-today-target-weeks`]

**Dependency:** Story 1.3 is Done and provides the current typed repository context, live/demo honesty, Supabase owner-scoping patterns, server-action feedback, CLI-first precedent, and Apple-inspired responsive design system.

## Acceptance Criteria

1. **Named physical-mail campaigns.** The realtor can create a campaign with a required human-readable name and optional internal notes. The UI consistently describes printed mail/postcards and never presents this feature as email marketing or Mailchimp.
2. **Per-contact checklist.** Selecting a campaign shows the CRM contacts and whether each has received it. Every checkbox has an accessible contact-specific label, a pending state, and explicit success/error feedback; a failed mutation does not visually claim the row was saved.
3. **Automatic send date.** Marking a contact records the current calendar date as `sentOn` and displays it after persistence. Clearing the checkbox removes that send record. Repeated mark/unmark commands are idempotent.
4. **Persistent history and summaries.** Campaign progress survives navigation and reload in the active repository. Each campaign shows sent, remaining, and total eligible-contact counts, and the selected campaign retains historical send dates even when another campaign is opened.
5. **Safe server-validated commands.** Campaign names/notes and campaign/contact identifiers are validated outside React. A send can only link an owner’s campaign to the same owner’s contact; missing resources, cross-owner targets, malformed input, and repository failures produce useful errors without partial false success.
6. **Live and demo parity.** A UI-independent mailer repository supports the seeded in-memory mode and Supabase mode with the same observable behavior. Demo state survives development HMR; live queries and writes include explicit owner filters even when RLS also applies.
7. **Forward-only database hardening.** A migration upgrades `mailer_sends` to carry owner scope and same-owner composite foreign keys, preserves existing rows, maintains one send per campaign/contact, and replaces the original RLS policy with owner-bound checks. The migration does not rewrite or drop contact history.
8. **CLI-first operation.** Before relying on the UI, a CLI can list campaigns, create a campaign, mark a contact sent, and unmark it through the same application/repository boundary. It emits machine-readable output, uses explicit commands/arguments, refuses malformed operations, and never calls a browser component.
9. **Apple-inspired responsive experience.** `/mailers` replaces the preview-only matrix with a calm campaign workspace that reuses `--sk-*` tokens, native/system typography, grouped surfaces, 44px controls, visible focus, reduced motion, light/dark themes, and a usable 390px layout for up to the approved 200–500 contacts.
10. **Regression protection.** Focused tests cover validation, summary math, mark/unmark idempotency, same-owner enforcement, memory persistence, Supabase owner filters, repository failures, and existing contact/cadence/import behavior. Lint, typecheck, tests, CLI smoke, production build, and responsive runtime review pass.

## Out of Scope

- Email campaigns, templates, scheduling, delivery, analytics, or replacing Mailchimp.
- Mailchimp API synchronization or unsubscribe webhooks; those remain a separate integration story.
- Printing, label generation, postal-service integration, postage purchasing, or address verification.
- Campaign deletion, archival workflows, bulk destructive actions, or editing past send dates.
- Contact segmentation engines, saved audiences, household merging, or automatic campaign enrollment.
- New libraries, state managers, ORMs, queues, caching layers, or worker services.

### Product and UX Boundaries

- The approved feature is physical mailer tracking: named mailers, one checkbox per contact, and an automatic date. [Source: `docs/prd/requirements-analysis-v2.md#phase-1--the-thing-shes-missing-today-target-weeks`]
- Mailchimp remains the email campaign tool; Phase 1 must not build generic campaigns inside the CRM. [Source: `docs/prd/requirements-analysis-v2.md#3-the-most-valuable-thing-she-wrote`]
- The product must be mobile-first and premium, while the approved scale is only 200–500 contacts; server components and bounded synchronous work are sufficient. [Source: `docs/architecture/tech-stack.md#constraints-driving-the-decision`; `docs/architecture/tech-stack.md#decision`]

### Architecture and Data Boundaries

- Use Next.js 15 App Router, TypeScript, Tailwind CSS v4 tokens, Supabase/Postgres, and the existing typed repository pattern. No component library, ORM, state manager, or separate service is authorized. [Source: `docs/architecture/tech-stack.md#decision`; `docs/architecture/tech-stack.md#data-layer-approach-for-phase-1`]
- `0001_init.sql` already defines `mailers(id, owner_id, name, notes, created_at)` and `mailer_sends(mailer_id, contact_id, sent_on)`. It also enables RLS, but `mailer_sends` does not carry owner identity; harden it forward in `0003` rather than editing applied migrations.
- `0002_contact_import_intake.sql` adds `contacts_id_owner_unique`, enabling a same-owner composite contact foreign key. The new migration must provide an equivalent `(id, owner_id)` uniqueness constraint on `mailers` before adding composite send references.
- Preserve one send per `(mailer_id, contact_id)` and treat row existence as the checked state; `sent_on` is a date rather than a timestamp because the requirement is a calendar-day mailing record.
- The UI must call server-validated application commands; React must not write directly to Supabase or reproduce validation/business rules.

### CLI and Error Handling

- Article I of the project Constitution requires full CLI operation before UI. The CLI should use the same mailer commands/repository, return JSON, and use non-zero status for invalid/missing resources or persistence failure.
- The in-memory CLI process is intentionally ephemeral across separate invocations. A deterministic in-process smoke harness or scripted scenario may exercise create/mark/unmark together; do not falsely claim durable cross-process demo storage.
- Do not log contact PII, campaign notes, raw form data, or database credentials in errors. Operator-facing failures should name the operation without leaking payloads.

### Testing

- Use the existing Vitest configuration and adjacent `*.test.ts` files for pure commands/repositories; add focused owner-filter tests for Supabase query construction.
- Required cases: invalid/empty/oversized campaign name; notes bound; create/list; repeated mark; repeated unmark; missing campaign/contact; same-owner mismatch; correct summary counts/dates; repository failure; demo HMR singleton; live query owner filters.
- Runtime path: create campaign → select campaign → check contact → persisted date/count → reload → uncheck → restored remaining count, at desktop and 390px in light/dark with keyboard focus and zero console errors.
