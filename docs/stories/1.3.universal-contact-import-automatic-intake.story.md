## Story

**As a** solo real estate agent,  
**I want** to import contacts exported from the tools I already use and accept new leads automatically through a secure intake channel,  
**so that** my CRM becomes the reliable contact system without retyping 200–500 records or creating duplicates.

**Traceability:** Phase 1 explicitly includes importing contacts from spreadsheet, phone, and Mailchimp exports; the client also requested that future website form submissions automatically become CRM contacts. Boldtrail access remains unanswered, so its CSV is supported as a best-effort preset without promising direct account connectivity. [Source: `docs/prd/requirements-analysis-v2.md#2-blockers-resolved`; `docs/prd/requirements-analysis-v2.md#41-she-said-yes-to-gmail-d--but-it-does-not-fit-her-lead-sources-`; `docs/prd/requirements-analysis-v2.md#51-boldtrail-export--never-answered-and-now-more-worrying-`; `docs/prd/requirements-analysis-v2.md#52-a-website-is-a-second-project-`; `docs/prd/requirements-analysis-v2.md#7-recommended-phasing`]

**Dependency:** Story 1.2 is Done and provides server-validated contact commands, the repository boundary, live/demo persistence modes, responsive form patterns, and explicit mutation feedback.

## Acceptance Criteria

1. **Multi-source file import.** From Contacts, the realtor can open an Import Contacts workspace and select a `.csv` or `.vcf` export. Presets cover generic spreadsheets, Mailchimp, Google Contacts/Android, Apple Contacts/iPhone, and best-effort KvCore/Boldtrail exports without claiming direct access to those accounts.
2. **Preview before persistence.** File contents are parsed and validated on the server with bounded file/row limits. Before any write, the realtor sees the detected format/source, recognized fields, total rows, planned creates/updates/skips/rejections, and row-level reasons. Canceling or a failed preview writes nothing.
3. **Contact-model mapping.** Common aliases map into the existing Contact model, including name, preferred name, phone, secondary phone, email, address, birthday, home-purchase date, Hot/Warm/Nurture, relationship, intent, source, pipeline stage, tags, subscription state, external id, and a first-class note when present. Unknown columns are reported, not silently treated as supported fields.
4. **Conservative deduplication and merge.** Import matching uses a source/external-id link when available, then normalized email, then normalized phone. A match fills empty fields only and never overwrites a non-empty CRM value during bulk import. Duplicate rows in the same file collapse deterministically; identical notes are not appended twice. Re-importing the same source data is idempotent.
5. **Honest completion results.** Confirming a valid preview persists through the existing repository boundary, schedules cadence for new active contacts, and reports created, updated, skipped, rejected, and notes-added counts. Partial row failures remain explicit and do not turn into a global success claim; affected contact/list/triage routes are revalidated after confirmed writes.
6. **Secure automatic intake.** A platform-neutral JSON endpoint accepts website or external-platform pushes in bounded batches. It requires a server-only bearer token, an owner binding, a source name, external ids, and an idempotency key; rejects unauthenticated, malformed, oversized, replay-conflicting, or half-configured requests with useful 4xx/503 responses; and never silently falls back from configured live persistence to demo memory.
7. **Persistent provenance and replay protection.** Supabase stores owner-scoped external contact links and intake receipts with RLS, unique constraints, request hashes, response receipts, and timestamps. Server-side privileged access, when configured for automatic intake, remains secret and every data query is explicitly owner-scoped even though the client is privileged.
8. **CLI-first import engine.** Parsing, source detection, mapping, validation, deduplication, planning, and execution live outside React and route handlers. A CLI command can preview an export and, only with complete live credentials plus an explicit commit flag, run the same engine against the configured owner; it refuses ephemeral demo commits.
9. **Apple-inspired responsive experience.** The import workspace reuses the established `--sk-*` system, native/system typography, grouped surfaces, explicit focus and error states, 44px actions, reduced-motion behavior, light/dark themes, and 390px responsiveness. File contents and contact PII never enter the URL or browser storage.
10. **Regression and security protection.** Focused tests cover quoted/multiline CSV, vCard, source aliases, invalid rows/dates/enums, duplicate rows, existing-contact merge, note idempotency, file/row/batch bounds, idempotency replay/conflict, bearer-token checks, owner scoping, repository failures, and existing cadence/triage behavior. Lint, typecheck, tests, CLI smoke, production build, and focused runtime review pass.

## Out of Scope

- OAuth or direct pull connectors for Mailchimp, Google Contacts, Apple/iCloud, KvCore/Boldtrail, Zillow, or any unnamed platform.
- Full Mailchimp two-way synchronization, conflict reconciliation, tag push, or unsubscribe webhook; Phase 1 still recommends CRM → Mailchimp plus unsubscribe-in as a separate integration story.
- Gmail lead-email parsing, which remains an open client decision.
- Instagram/Facebook DM ingestion, explicitly deferred by the client.
- Building or hosting the realtor website; only the CRM-side intake contract is included.
- Remote URL imports, background scraping, social enrichment, destructive overwrite, contact deletion, or automatic merging on name alone.
- Files above the documented safe limit or imports above 1,000 rows; the approved dataset is 200–500 contacts.

- The approved scale rules out queues, caching layers, sharding, or other large-system machinery. Bounded synchronous batches are appropriate for 200–500 contacts. [Source: `docs/architecture/tech-stack.md#constraints-driving-the-decision`]
- No component library, state manager, ORM, or separate worker service is authorized. Use existing Tailwind tokens, server components/actions where practical, and pure TypeScript functions. [Source: `docs/architecture/tech-stack.md#decision`]

### Security and Error Handling

- Import files and webhook bodies are untrusted PII. Enforce content, byte, row, and batch limits before work; validate every enum/date/value on the server; never log raw contact payloads, tokens, or file contents.
- Do not accept arbitrary remote URLs, do not expose service credentials to client bundles, and do not allow middleware session redirects to substitute for webhook token authentication.
- Automatic intake must fail closed when token, owner, Supabase URL/key, or live persistence is incomplete. Demo memory is acceptable for authenticated UI import but not an honest automatic production feed.
- A privileged live client bypasses RLS; if used for machine intake, every query must additionally filter the configured owner and tests must prove cross-owner rows are not addressed.
