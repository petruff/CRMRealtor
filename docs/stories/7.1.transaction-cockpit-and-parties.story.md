## Story

As a Florida realtor, I need each buyer, seller, listing, lease, and referral transaction to have a complete operational record, so I can manage the deal without confusing transaction state with the contact relationship pipeline.

## Acceptance Criteria

1. Transaction kind supports buyer, seller, listing, lease, and referral while representation side remains an independent bounded field.
2. A transaction stores an explicit title, primary contact, optional additional parties, property reference or bounded manual address, responsible membership, source snapshot, status, next action, dates, and version.
3. Parties have a bounded role, contact link when available, display label, communication participation flag, and append-only history; they do not create or merge contact identity implicitly.
4. Transaction status changes use an optimistic version, append history, retain actor/time/reason, and never silently change contact lead type, relationship status, or pipeline stage.
5. Existing `real_estate_transactions` rows remain readable and migrate deterministically to the compatible default transaction kind.
6. Owner and active assistant may perform ordinary transaction work; ownership, connector, AI-secret, and support-only boundaries remain unchanged. Revoked and cross-workspace actors fail closed.
7. The cockpit provides bounded summary, filters, search, active/closed grouping, next action, parties, deadlines, financial snapshot, and a clear empty/missing-data state on desktop and mobile.
8. Create, edit, party, and transition commands are idempotent and return user-safe errors plus redacted support references for uncertain failures.
9. No contact, transaction, party, history, or property detail leaks across workspaces through UI, repository, RPC, direct table read, or guessed identifiers.
10. Migration replay, rollback/forward repair, RLS, unit, repository, command, responsive, accessibility, lint, typecheck, full tests, and build pass.
