## Story

**As a** realtor or authorized workspace assistant,  
**I want** a conversational Omnix copilot that deterministically answers from the CRM records I am allowed to see,  
**so that** I can understand today's priorities, deadlines and follow-ups without waiting for an AI provider or risking unsupported actions.

**Traceability:** additive foundation for D-12, L-16, A-02 and B-06 in `docs/prd/omnix-reference-parity-matrix.md`; prerequisite for Story 5.1 in `docs/prd/omnix-crm-parity-roadmap.md`. It extends the real deterministic intelligence delivered by Story 2.1 and the task/activity authority delivered by Story 3.1; it does not claim generative-AI parity.

**Dependencies:** Stories 2.1, 3.0 and 3.1 are Done and supply the deterministic Omnix snapshot, `/omnix`, canonical `WorkspaceScope`, owner/assistant membership, RLS, workspace-scoped tasks/activities and authenticated CLI patterns. Stories 3.2 and 3.3 are not prerequisites: richer contact facts, archive state, cross-app search and event-backed analytics must appear only when their own capabilities are present and must otherwise degrade honestly.

## Acceptance Criteria

1. **CLI-first entry point.** A documented `npm run omnix:copilot -- <brief|ask|alerts|help> [options]` command works without React/browser imports before conversational UI is enabled. `brief` accepts `--today <YYYY-MM-DD>`; `ask` accepts exactly one `--question <text>`; all operational commands accept explicit `--live`. Question input is 1–200 printable characters, rejects control characters, and one invocation resolves at most one supported intent. Output uses a stable `omnix-copilot.v1` JSON envelope with `ok`, command, resolved intent, correlation ID, `sample | live` data mode, as-of time, answer blocks, citations, read-only suggestions and warnings. Existing `npm run omnix:brief` remains backwards compatible and delegates to the same deterministic brief builder or proves equivalent output.
2. **Closed conversational grammar.** The deterministic parser supports only these canonical intents: `brief [today|YYYY-MM-DD]`; `alerts [today|YYYY-MM-DD]`; `find contact <query>`; `pipeline`; `tasks <overdue|today|upcoming>`; `tasks from <YYYY-MM-DD> to <YYYY-MM-DD>`; `dates <today|upcoming>`; `mailers [<campaign-id>]`; `activity <contact-id>`; `connections`; and `help`. A documented fixed alias table maps exactly: “what should I do today” → `brief today`; “who needs attention” → `alerts today`; “show overdue follow-ups” → `tasks overdue`; “show today's tasks” → `tasks today`; “show upcoming dates” → `dates upcoming`; “show pipeline” → `pipeline`; “show mailers” → `mailers`; “show recent activity for <contact-id>” → `activity <contact-id>`; and “connection status” → `connections`. Matching is case-insensitive and tolerates terminal punctuation, but does not infer synonyms, intent, entities or missing dates beyond this table. Unknown/ambiguous questions return `unsupported-intent`, the supported examples and no data mutation.
3. **Authorized internal source boundary.** Every request uses authenticated membership-derived `WorkspaceScope` and the existing contact, activity and physical-mailer application/repository seams; live access remains protected by membership-derived RLS. The caller cannot supply owner/workspace authority, use service role as interactive authority, probe another workspace, or learn whether a forbidden record exists. Contact/pipeline results are capped at the existing 500-contact Smart List scale; task/activity results retain the existing 1–500 limit; query text retains the existing 200-character bound; record IDs retain the existing 1–128-character allowlist. Briefs default to aggregates and record IDs/links; names, contact points, notes or task text appear only for an explicit matching list/detail intent and only when authorized.
4. **Deterministic daily brief.** Given the same authorized repository state, configured CRM calendar zone and explicit as-of clock, the brief returns the same ordered result in CLI and UI. It preserves `buildWorkspaceSnapshot` and the existing triage rules: first contact; overdue and due-today follow-ups; seven-day upcoming follow-ups; seven-day birthdays; thirty-day home-purchase anniversaries; missing mailing addresses; and active/under-contract contacts without a next touch. After Story 3.1 is Done it additionally includes open tasks grouped as overdue, due today and upcoming seven days using `sortTasksForWorkQueue`. `OMNIX_TIME_ZONE`, when configured, defines the realtor's day; invalid configuration fails explicitly, while omission retains the documented local-process calendar behavior. No generated narrative may alter counts, order, dates or evidence.
5. **Explainable internal alerts and deadlines.** The alert catalog is limited to `needs-first-contact`, `overdue-follow-up`, `due-today-follow-up`, `upcoming-follow-up`, `birthday`, `homeaversary`, `pipeline-missing-next-touch`, `mailer-missing-address`, `task-overdue` and `task-due-today`. Each alert contains a deterministic ID derived from rule + source record + as-of date, category, priority/order, exact rule reason, as-of time, affected record ID, citations and safe review link. Alerts with the same rule/source/as-of date deduplicate; dismissed/acknowledged state, push/email notifications, random badges and background scheduling are not introduced. Contact pipeline stage is not interpreted as a transaction or contract deadline.
6. **Record-level citation contract.** Every factual answer item, count, deadline, alert and suggestion includes `citation.v1` entries with an allowlisted entity type (`contact | task | activity | mailer | mailer-send`), authorized record ID, exact fact/field keys used, source timestamp when the record supplies one, response as-of time and safe in-product target. Aggregate answers include citations for the bounded contributing record set plus the named deterministic rule. Citations are filtered through the same `WorkspaceScope` as the answer and cannot disclose a record the caller cannot open. A zero-match answer states the applied deterministic query and “no authorized record matched”; unavailable data is never replaced by a guessed fact.
7. **Read-only suggestion and mutation boundary.** Copilot responses and suggestions are side-effect free: they may point to a contact, work queue, physical-mailer campaign or existing command surface and may show a copyable preview, but they contain no executable closure/tool and never invoke a write. This story adds no copilot mutation endpoint. If the user chooses to act, the product navigates to or explicitly submits the existing application command (for example task create/transition or contact touch) with the exact target visible; the user must perform that separate explicit submission, and the existing command remains the sole validation, authorization, idempotency and activity-event authority. The copilot never sends, schedules, marks a mailer sent, changes pipeline/contact/task state or treats conversational text as confirmation.
8. **Honest capability evolution.** Story 3.6 reads the current contact `pipelineStage` as the pipeline fact and never creates a second pipeline source. Story 3.2 rich fields/archive/households and Story 3.3 persisted pipeline/search/counters are exposed only through additive adapters after those stories are Done; until then the copilot returns `capability-unavailable` for such a request and continues with supported facts. The `connections` intent reports that persisted workspace account status is unavailable until Story 3.5 and a connector are Done, links safely to `/connections`, and labels current page content as product capability disclosure—not real authorization or provider health. There is no silent sample fallback after a live failure.
9. **Additive conversational `/omnix` UI.** `/omnix` retains the existing daily brief, deterministic recommendation rules, explicit no-generative-model/no-autonomous-action disclosure and Apple-inspired Omnix/Cyryx Labs presentation. It additively provides a keyboard-operable conversational panel using the same parser/service/output contract, supported-prompt examples, per-answer citations, source links, read-only suggestion links, clear-session control and explicit pending/empty/unsupported/unavailable/error states. Session messages are page-session state only and are not presented as durable history. Desktop and 390px layouts, light/dark themes, reduced motion, focus visibility, semantic live-region behavior and no horizontal overflow pass.
10. **No-model security and observability.** No LLM SDK, model secret, provider credential, external network lookup, arbitrary SQL, shell/filesystem access, URL fetch, eval loop or hidden system prompt is introduced. User and stored text remain inert data inside the allowlisted parser/query contracts; HTML/script/control/path-like payloads cannot change intent or invoke a command. Structured redacted telemetry records correlation ID, workspace/membership identity, resolved intent, sample/live mode, as-of time, result/citation counts, duration and safe error category without dumping contact PII, question bodies, notes or task descriptions. Unsupported and forbidden requests are observable failures, not fake successful answers.
11. **Quality evidence.** Unit tests cover all canonical phrases and exact aliases, normalization, 200-character/control-character rejection, ambiguity/unknown handling, date parsing, deterministic ordering, brief compatibility, every alert rule/dedupe and citation construction. Application/repository tests cover missing/available optional capabilities, zero results, 500-record bounds, owner/assistant/revoked membership, two workspaces, forbidden IDs, redaction and no-write spies for every intent. CLI smoke proves sample/live disclosure, stable schema and non-zero failures; browser QA proves the conversational panel, citations and unsupported/unavailable states at desktop/390px in both themes with keyboard/screen-reader semantics. `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` pass.

### Assistant vocabulary and invariants

- **Conversational:** a chat-shaped interface over a documented fixed grammar; it does not imply probabilistic language understanding.
- **Fact:** a value read from an authorized record or a deterministic aggregate over cited records as of an explicit clock.
- **Citation:** a workspace-authorized pointer to the record fields that establish a fact; it is not a generated bibliography.
- **Suggestion:** read-only guidance/link/command preview. It is never an action and never proves that a mutation or provider operation occurred.
- **Deadline:** a stored contact follow-up date, Story 3.1 task due time, birthday or home-purchase anniversary window. Pipeline stage alone does not create a contract/deal deadline.
