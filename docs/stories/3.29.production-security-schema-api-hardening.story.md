## Story

**As the owner and developer of Judith's CRM,**
**I want** privileged database operations, API authentication, schema adoption and operational screens to behave securely and consistently,
**so that** Judith and her assistant can use Production without technical leakage, silent capability loss or unsafe access paths.

## Acceptance Criteria

1. A current, non-empty Production database backup is captured and read back before any remote DDL; the release receipt records the backup artifact, checksum, restore verification and an explicit rollback path for every migration in this story.
2. Connector-worker RPCs that claim jobs or read/write connector secret envelopes cannot be executed by `public`, `anon` or `authenticated`. Only the service worker role retains the minimum required execution privilege.
3. New privileged functions are fail-closed by default. The migration revokes unsafe default function privileges and explicitly grants each user-facing RPC that must remain callable; no blanket revocation breaks legitimate authenticated CRM operations.
4. Database tests enumerate the privileged connector RPC ACLs and fail whenever an end-user role can execute them. Security-definer functions changed by this story use a fixed `search_path`, schema-qualified objects and least-privilege grants.
5. Migrations 0027 and 0028 replay cleanly in a fresh local database. Production preflight detects whether `list_contact_alias_group_ids` and `apply_exact_contact_merge` exist before application code depends on them; missing required capability is observable and is not hidden behind an unlabelled fallback.
6. `/api/v1/*` requests are not redirected to `/welcome` by browser-session middleware. Each API route remains responsible for its own API-key, signature or provider-webhook authentication and returns a JSON `401` or `403` when unauthorized.
7. Duplicate auditing resolves contact alias groups in bounded database calls rather than one request per contact. A missing capability cannot produce repeated 404 traffic or a multi-second N+1 path.
8. Operational screens use human names, roles and readable references instead of raw contact, workspace or correlation UUIDs wherever a person must act. The incomplete-contact status control has an accessible label, and route loading copy describes the surface being loaded without exposing internal terminology.
9. Production verification includes database advisors/logs, API auth behavior, authenticated desktop/mobile smoke tests at 390, 768 and 1440 widths, and owner-versus-assistant permission checks. External provider authorization that only Judith can grant remains explicitly `UAT pending` rather than simulated.
10. Existing Production contacts, workspaces and imports are audited read-only in this story. No contacts are merged, deleted, reclassified or reimported without a separately reviewed reconciliation plan and rollback receipt.
11. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, database tests and `git diff --check` pass before release handoff. Commit, push and Production promotion are performed only by `@devops` after all applicable safety gates pass.

## Audit Evidence

- Production grants `anon`, `authenticated` and `service_role` execution on `claim_connector_jobs`, `read_connector_job_secret_envelope` and `store_connector_connection_secret`; the current migration revokes only `public`.
- Production logs repeatedly request the absent `list_contact_alias_group_ids` RPC, while the duplicate-audit path performs alias lookup once per contact and silently treats a missing capability as an empty mapping.
- Production does not expose the 0027/0028 exact-identity capabilities expected by the current application release.
- Requests to `/api/v1/status`, `/api/v1/contacts` and webhook routes are intercepted by session middleware and redirected to `/welcome` before route-owned authentication executes.
- Insights, workspace assignment and connection diagnostics display raw UUIDs in user-facing action surfaces; the incomplete-contact status selector has no accessible label.

## Architecture Constraints

- Postgres remains the durable authority; privileged connector work is service-only.
- Every `SECURITY DEFINER` change uses fixed search paths, schema-qualified objects and explicit execution grants.
- Browser session auth and operational API auth remain separate trust boundaries.
- Database changes are forward-only and reversible through a tested compensating migration or restore procedure; no destructive remote change precedes backup evidence.
- User-facing RPCs are inventoried before grant changes. Broad privilege cleanup cannot be used as a substitute for route-by-route authorization review.

## Autonomous Decisions

- [AUTO-DECISION] Apply remote DDL before a verified backup because the security issue is critical → No; local mitigation and migration preparation proceed immediately, but Production mutation remains fail-closed.
- [AUTO-DECISION] Revoke execution from every authenticated security-definer function → No; only privileged/internal functions are restricted until every intentional client RPC is classified.
- [AUTO-DECISION] Consolidate the three similarly named workspaces during hardening → No; ownership and data reconciliation are a separate reviewed operation.
- [AUTO-DECISION] Upload Judith's workbook or client data as a release test → No; fixtures and aggregate read-only evidence are used.
