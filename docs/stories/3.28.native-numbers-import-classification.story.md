# Story 3.28 — Native Numbers Import and File-Accurate Organization

**Epic:** 3 — CRM operating foundation
**Status:** Done
**Owner:** @sm (Chronos)
**Created:** 2026-08-23 from Judith's reported Apple Numbers import failure

## Story

**As Judith,**
**I want** Omnix to read my contact workbook directly and organize every valid contact from the status already present in the file,
**so that** I can import my database without format conversion, false limit errors or manual pipeline cleanup.

## Acceptance Criteria

1. Native `.numbers` files are handled as bounded binary workbooks in the browser and server; their ZIP/package bytes are never decoded as CSV text.
2. The supplied `contacts omnix.numbers` file previews all 144 named rows without the false `A cell exceeds 4,096 characters` error and without persisting contacts during verification.
3. Existing CSV, VCF, XLS and XLSX size, formula, cell-count, column-count, package-expansion, timeout and worker-isolation protections remain effective. Numbers packages receive the same applicable ZIP and worker protections.
4. Explicit `Lead Type`, `Relationship`, `Intent`, `Source` and `Pipeline Stage` columns remain authoritative. Common realtor labels in the supplied file are normalized deterministically: `client`, `active lead`, `client`, `archived`, `prospect`, `new lead`, `cold call`, `manual add`, `lead import`, `organic website` and `direct website`.
5. When lead type is blank, canonical relationship/pipeline evidence and Hot/Warm/Nurture tags supply the deterministic classification. Explicit Hot/Warm/Nurture values always win.
6. Import preview shows the final lead type and pipeline before save. On confirmed standard spreadsheet imports, matching active contacts receive the reviewed organizational fields from the file instead of retaining stale import defaults; the protected First Class repair path plus archived and ambiguous identity safety gates remain unchanged.
7. No source label silently grants email or SMS consent. Duplicate resolution remains based on existing external-ID/email/phone rules, never names alone; distinct emails or external IDs prevent a phone-only household merge.
8. Focused tests cover binary routing, native-format acceptance, human-label normalization, explicit precedence, inferred classification and matched-contact organization updates.
9. The real workbook receives a read-only acceptance run with aggregate counts only. No names, emails, phone numbers or raw notes enter test output or telemetry.
10. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` and `git diff --check` pass before release handoff. Commit, push and Production deployment require a separate explicit request.

## Root Cause Evidence

- The browser's binary-file check only recognized `.xls` and `.xlsx`; `.numbers` was decoded as text and its package bytes triggered the CSV cell-length guard.
- The server extension gate did not declare `.numbers`, although the installed SheetJS runtime successfully reads the supplied native workbook as one worksheet with 144 named rows, 20 columns and a maximum material cell length of 153 characters.
- The file uses customer-facing labels that were not accepted by the canonical enum parser, including `client`, `active lead`, `archived`, `prospect`, `new lead`, `manual add` and `cold call`.
- Existing-contact import patches filled identity gaps but did not apply reviewed relationship, lead type or pipeline changes.
