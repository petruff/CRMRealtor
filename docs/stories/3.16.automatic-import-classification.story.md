# Story 3.16 — Automatic Imported-Contact Organization

**Epic:** 3 — CRM operating foundation  
**Status:** Done  
**Owner:** @dev (Vulcan) with @data-engineer (Ceres)  
**Created:** 2026-08-21 from the owner request to eliminate manual classification after import

## Story

**As Judith,**  
**I want** contacts to be classified and scheduled automatically from the information already present in each imported file,  
**so that** importing a database creates an immediately usable CRM instead of leaving roughly 140 records for manual cleanup.

## Acceptance Criteria

1. Every valid imported contact leaves preview with a complete operational classification: Hot/Warm/Nurture, qualification state, relationship, intent, source and pipeline stage.
2. Explicit canonical values supplied or deliberately mapped by the user always win. Automatic classification only fills missing organizational fields and never silently overwrites explicit file data.
3. First Class/KvCore source facts — including lifecycle Status, 0–5 Rating, Last Closed Date, Deal Type and tags — are interpreted through deterministic, versioned rules. Recognized contract/appointment/active/client/past-client/sphere/lost states map to the corresponding Omnix fields.
4. Rating 4–5 maps to Hot, 2–3 to Warm and 0–1 to Nurture when lead temperature is absent. Strong lifecycle states may supply a safe temperature when rating is absent; unknown records become Nurture + Needs review rather than being presented as confidently Warm.
5. The preview explains how many records were organized automatically, how many used explicit values and how many received a safe Needs-review fallback. Row-level preview shows the resulting classification and a plain-language reason without exposing internal keys.
6. New contacts receive cadence from the final classification. Closed/lost contacts receive no follow-up; active contacts receive the existing automatic cadence and remain manually adjustable afterward.
7. A workspace-admin repair operation can organize previously imported contacts. It is dry-run first, idempotent, bounded, records activity, and skips archived contacts, contacts without import provenance, manually edited/touched contacts and contacts whose organizational fields no longer match the old import defaults.
8. The current Judith workspace is dry-run audited before repair. Aggregate counts only are logged or returned; no PII or raw source values appear in telemetry.
9. Classification logic remains UI-independent and provider-bounded; no generative model, external enrichment, inferred messaging consent or name-only identity merge is introduced.
10. Focused tests cover every rule, explicit-value precedence, fallback behavior, preview counts, cadence, safe repair skips and idempotency. Lint, typecheck, full tests, build and authenticated production verification pass.

## Classification Policy v1

- Precedence: explicit canonical value → recognized lifecycle/date/rating evidence → safe fallback.
- Contract/pending/escrow → Active client, Under contract, Hot.
- Appointment/meeting → Lead, Appointment set, Hot.
- Active client → Active client, Actively working; Active lead → Lead, Actively working.
- Last Closed Date or past/closed/sold lifecycle → Past client, Closed.
- Sphere/SOI → Sphere, Contacted. Lost/inactive/archive/dead/trash → Lead, Lost.
- Rating 4–5 → Hot; 2–3 → Warm; 0–1 → Nurture.
- Unknown lifecycle/rating → Lead, New, Nurture, Needs review.
- Source consent facts remain evidence only and never enable email/SMS authorization.
