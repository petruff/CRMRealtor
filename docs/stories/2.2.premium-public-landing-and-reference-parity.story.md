## Story

**As a** prospective or returning realtor,  
**I want** a premium public introduction to Omnix with truthful sign-in and product evidence,  
**so that** I can understand the Cyryx Labs product, evaluate its current capability coverage and enter the existing workspace safely.

## Acceptance Criteria

1. A premium public landing is available at **`/welcome`**, clearly branded **Omnix — Powered by Cyryx Labs**, and explains who the product serves, what it does now and how a user proceeds without requiring an authenticated session.
2. The landing offers **Google sign-in through Supabase OAuth using basic identity scopes only** (`openid`, `email`, `profile`). It does not request Gmail, Calendar or other expanded provider scopes in this story, does not capture a Google password, and exposes accessible loading, success, cancellation and failure states.
3. The public experience communicates the environment honestly: demo/sample-backed content is visibly identified as demo, OAuth setup or unavailable live configuration is not presented as a working production connection, and no fabricated customers, performance metrics, integrations, AI capability or business outcomes are shown.
4. All existing routes and capabilities are preserved. Public chrome for `/welcome` is visually and structurally separate from the authenticated/internal application shell; adding the landing must not render internal navigation on the public page or replace the existing Today, Contacts, Mailers, Connections, Workspace, Pipeline, Insights or Omnix destinations.
5. The landing includes at least one **real screenshot captured from the current Omnix product runtime**, not from RealtorsPal, a mockup or a proprietary asset. The image is legible, has meaningful alternative text or an equivalent accessible description, is optimized for delivery, and does not expose private contact data, tokens, secrets or developer tooling.
6. A clean-room, exhaustive RealtorsPal capability-parity matrix is maintained from independently observed public evidence. Every inventoried reference capability is classified exactly once as **real**, **partial**, **simulated** or **absent** in Omnix, with concise Omnix evidence and an honest gap/next-step note; unknowns remain unknown. No proprietary RealtorsPal source code, assets, copy, branding or implementation detail is copied into the product or repository.
7. Successful authentication and public-to-internal navigation use **safe internal redirects**: only same-origin application paths from an explicit allowlist are accepted; external URLs, protocol-relative values, malformed values and unapproved paths fall back to a safe default internal destination. Authentication errors return to a safe public state without leaking provider or credential details.
8. `/welcome` is complete at **390px and desktop widths**, has no horizontal overflow, and preserves the deliberate light and dark themes. Semantic landmarks and headings, keyboard navigation, visible focus, accessible names, contrast, reduced-motion behavior and appropriately sized touch targets meet the project accessibility standard.
9. `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` pass. Browser QA covers `/welcome`, authentication entry/error behavior, safe redirect cases, the real product screenshot, representative preserved internal routes, 390px and desktop layouts, light/dark themes, keyboard operation, semantic navigation, zero unexpected console errors and zero broken local assets.

## Out of Scope

- Copying, translating, rebranding or modifying proprietary RealtorsPal/Realdash code, assets, screenshots, copy or trade dress.
- Gmail, Google Calendar or other incremental OAuth scopes; refresh-token integrations; Mailchimp, Twilio, Meta, MLS or autonomous external actions.
- Claiming production OAuth readiness when Supabase/provider configuration or credentials are absent.
- Rebuilding, renaming or removing existing internal routes, features, mobile destinations or the current authenticated shell.
- Implementing every parity gap identified by the clean-room matrix; gaps become evidence for separately approved stories.
- New customer claims, testimonials, invented metrics, pricing, checkout, billing, publishing or production deployment.

## Dev Notes

### Product and Governance Boundaries

- Story 2.1 established **Omnix — Powered by Cyryx Labs**, the Apple-inspired tokens, light/dark behavior, honest demo/live boundaries, and the preserved Today, Contacts, Mailers, Connections, Workspace, Pipeline, Insights and Omnix destinations. This story is additive and must not regress those contracts. [Source: `docs/stories/2.1.omnix-rebrand-intelligence-workspace.story.md#acceptance-criteria`]
- RealtorsPal is a proprietary reference. Use only public, independently observable capability facts to create a clean-room inventory; do not inspect, copy or derive from proprietary source code or assets. [Source: `docs/prd/omnix-product-expansion.md#product-decision`]
- A parity label means:
  - **real** — implemented and backed by current executable/product evidence;
  - **partial** — a material subset works, with the missing boundary named;
  - **simulated** — demo/sample/static behavior is visible but no live provider or durable capability is connected;
  - **absent** — no current Omnix implementation evidence exists.
- The parity matrix must be exhaustive relative to the reviewed public inventory, not a claim about unobserved proprietary functionality. Record the public source/evidence boundary and review date alongside the inventory.
- Public marketing claims must be traceable to shipped Omnix behavior. Setup affordances, roadmap items and demo content are not proof of a live integration.

### Authentication and Navigation Boundaries

- Use the existing Next.js App Router and Supabase authentication approach; keep credentials and configuration server-side where required. Never log tokens, authorization codes or provider error payloads containing sensitive values.
- Basic identity is the only OAuth authority in scope. Gmail/Calendar authorization must remain a later, explicit incremental-consent story.
- Normalize redirects before use. Accept only known internal pathname values, never arbitrary absolute URLs or user-controlled origins. The safe default should be an existing internal home route verified during implementation.
- `/welcome` must remain usable when OAuth configuration is absent: explain the limitation honestly and keep the product narrative accessible rather than displaying a broken or falsely successful CTA.

### Landing and Screenshot Boundaries

- The public chrome may share low-level brand/theme primitives, but it must not mount authenticated app navigation or imply that internal demo data belongs to the visitor.
- Capture product evidence from a locally running current Omnix build with sanitized/demo records. Review the entire frame for names, email addresses, phone numbers, browser bookmarks, environment URLs, tokens and console/dev overlays before accepting it.
- Keep essential claims as HTML text. The screenshot supplements the narrative and must have dimensions/aspect handling that prevents layout shift and overflow.

### Relevant Source Areas

- Expected implementation area: `packages/crm/app/` for route/layout/auth callback boundaries, `packages/crm/components/` for public presentation primitives, and `packages/crm/lib/` for reusable redirect/OAuth policy logic.
- Expected evidence/documentation area: `docs/` for the clean-room parity matrix and browser/QA evidence, plus a repository-controlled optimized image location selected consistently with current asset conventions.
- Do not assume exact new filenames beyond the required `/welcome` route; the developer must reuse established project organization and record every actual change in the File List.

### Autonomous Decisions

- [AUTO-DECISION] Where should successful OAuth return? → Use an explicit allowlist with an existing internal home route as fallback (reason: preserves deep-link utility without enabling open redirects).
- [AUTO-DECISION] Should the landing imply live Google productivity access? → No; request basic identity only and disclose missing/demo configuration (reason: expanded integrations are outside this story and require separate consent).
- [AUTO-DECISION] How is reference parity proven? → Public capability inventory plus Omnix route/test/runtime evidence (reason: clean-room comparison must not depend on proprietary implementation).
