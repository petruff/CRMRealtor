## Story

**As Judith, the realtor operating the workspace,**  
**I want** reversible note removal, a separate qualification queue, a governed choice of Omnix AI provider and a safe final migration workflow,  
**so that** I can correct CRM records, identify contacts whose priority is not yet known, use the preferred AI provider and complete migration without losing history or merging the wrong people.

**Traceability:** Judith feedback relayed on 2026-08-17; Stories 3.7, 3.14–3.17; current append-only note and encrypted workspace-AI boundaries.

**Dependencies:** Stories 3.0, 3.1, 3.7, 3.14, 3.16 and 3.17. Existing workspace authority, canonical duplicate resolution, Omnix supported-query parser and encrypted-secret model remain authoritative.

## Acceptance Criteria

1. Notes remain immutable, but an active workspace owner or assistant can archive a note with an explicit reason; archive records actor membership and timestamp and never deletes or rewrites the original body.
2. Archived notes are hidden from the default contact timeline, available through an explicit archived-notes disclosure, and restorable by an active authorized member with actor/time audit evidence.
3. Archive/restore commands are workspace-bound, idempotent for exact replay, fail closed for cross-workspace/stale/nonexistent notes and append redacted activity evidence without copying note text.
4. `Hot`, `Warm` and `Nurture` remain the only lead-temperature values and continue to own cadence, triage ordering and Mailchimp tags unchanged.
5. Contacts gain a separate qualification status `qualified | needs-qualification`; the user-facing label for the latter is `Figure out`, and existing contacts deterministically default to `qualified` without inferred source mapping.
6. Contact create/edit/detail, Contacts filtering and a bounded `Figure out` queue expose the qualification status accessibly; changing it does not alter lead temperature, pipeline stage, consent, cadence or Mailchimp state.
7. CLI/data export/import contracts can read and write the qualification status explicitly, while generic source `Status`/`Rating` values remain provenance unless the user maps them deliberately.
8. Workspace AI settings support exactly one active provider configuration selected from Google Gemini or Anthropic Claude. Provider, model and redacted key fingerprint are public workspace state; plaintext keys remain server-only encrypted envelopes.
9. Claude configuration is owner-only, validates the key with a bounded non-customer query, uses an allowlisted Anthropic Messages API model, supports optimistic rotation/disable/cryptoshred and never returns the key after submission.
10. Claude has the same read-only routing authority as Gemini: it may return one allowlisted deterministic Omnix query only, receives no CRM rows, cannot answer directly or execute mutations, times out and falls back to the deterministic parser on failure.
11. The First Class CSV/XLSX final import remains preview-first and production mutation is blocked until the authenticated Judith identity and target workspace are verified. Exact external ID, normalized email and canonical phone matching continue to prevent duplicate creation, while distinct external IDs/emails sharing a household phone remain separate.
12. Forward migration, rollback, pgTAP, unit/application/UI tests, CLI smoke, lint, typecheck, full tests and optimized build pass. No customer file, note body, API key or provider response is committed or logged.

## Out of Scope

- Hard deletion or in-place editing of note bodies.
- Adding `Figure out` as a fourth lead temperature or Mailchimp tag.
- Sending full contact records, notes or exports to Gemini or Claude.
- Connecting a consumer Claude.ai account, autonomous CRM mutations or importing into an unverified workspace.
