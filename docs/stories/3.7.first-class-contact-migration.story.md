## Story

**As a** realtor migrating from another CRM,  
**I want** Omnix to understand the real contact export, map operational facts to canonical CRM fields and preserve every non-empty source field,  
**so that** the complete contact base can be imported without silent loss, accidental reinterpretation or manual re-entry.

**Traceability:** User-supplied 1st Class Real Estate CSV/XLSX export audited on 2026-08-12; Story 3.4 portability boundary; Story 3.2 rich-contact/custom-field authority.

**Dependencies:** Stories 3.2 and 3.4. The parser, contact identity, atomic group import and workspace authority remain canonical and must be extended, not bypassed.

## Acceptance Criteria

1. CLI and UI recognize the audited 1st Class Real Estate export in CSV and XLSX, discover the actual header row within the first ten bounded rows, reject ambiguous/no-header workbooks, and produce the same 144-row preview for both files.
2. The import contract accounts for all 79 audited source headers. Each non-empty cell is either mapped to a canonical Omnix field/contact point or preserved as a typed, workspace-scoped source fact; no populated source column may be silently dropped.
3. Canonical mapping covers contact identity/name, primary email, cell/work/home/secondary phones, primary/secondary address facts, source, hashtags, email opt-in, source status/deal type and safe external identity. Source-specific enum values are normalized without making unsupported business inferences; the original value remains available as provenance.
4. Consent-sensitive fields (`Email Optin`, `Text On`, `Phone On`, `Valuation Optin`, `TCPA Optin Date`, `TCPA Optin Party`, `TCPA Optin Party ID`) are preserved with their source label/value and timestamp/provenance. They do not grant new Omnix messaging authorization unless an existing consent authority explicitly accepts that evidence.
5. Source facts persist atomically with each create/update/unchanged import group, are idempotent for exact replay, reject divergent replay, use membership-derived workspace authority, and never retain the raw file or another workspace's values.
6. Contact detail exposes a readable “Imported profile” section containing all preserved non-empty source facts, grouped by identity, ownership, real-estate preferences, engagement, verification and consent. Sensitive operational identifiers are not rendered outside the authorized workspace.
7. Preview reports field coverage (`canonical`, `preserved`, `empty`, `unsupported`) and blocks commit if any populated header has neither a canonical destination nor an approved source-fact destination. A reusable profile may retain the deterministic source schema version.
8. The importer handles duplicate identity, archived matches and invalid rows using existing preview/quarantine behavior; one bad row does not erase successful rows, and the aggregate receipt truthfully reports created/updated/unchanged/quarantined/failed outcomes.
9. A sanitized 79-column fixture (no Judith/contact PII) proves CSV/XLSX parity, shifted-header discovery, 144-row capacity, consent non-escalation, all-field coverage, source-fact display, replay safety and two-workspace isolation.
10. CLI smoke, focused parser/application/SQL/UI tests, Supabase reset/pgTAP, lint, typecheck, complete tests and production build pass before handoff. Real-file runtime validation may use only local transient buffers and must not commit raw customer data into the repository.

## Out of Scope

- Inventing missing values, treating engagement counts as activity events, restoring archived contacts automatically, or converting source opt-in flags into provider/legal authorization.
- Retaining the raw CSV/XLSX, storing arbitrary JSON blobs without field-level bounds, or creating a database column for every vendor-specific header.
- Automatically creating a spouse Contact when the source provides insufficient independent identity; spouse facts remain preserved for explicit review.
