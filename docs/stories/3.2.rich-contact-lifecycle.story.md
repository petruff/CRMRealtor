## Story

**As a** realtor or authorized assistant,  
**I want** rich household/contact records, workspace assignments and reversible contact lifecycle controls,  
**so that** relationship, property and responsibility context stays accurate without losing CRM history.

**Traceability:** D-08; L-12; L-23–L-27; I-06 in `docs/prd/omnix-reference-parity-matrix.md`.

**Dependencies:** Story 3.0 supplies canonical `WorkspaceScope`, membership-derived RLS and `owner | assistant` identity. Story 3.1 supplies workspace-scoped activities/tasks, archive-style state conventions and work-queue integration. This story does not create or alter workspace membership authority.

## Acceptance Criteria

1. **CLI-first lifecycle.** CLI commands add/update/list/archive/restore contact points, household relationships, workspace-member assignments, typed custom fields and the contact record itself without a browser. Commands use Story 3.0 `WorkspaceScope`, reuse validated application services, have stable exit codes and never authorize from caller-supplied workspace/owner values.
2. **Multiple contact points.** A contact supports multiple typed phone/email points with label, normalized value, primary flag, consent/subscription facts where already modeled and timestamps. There is at most one primary point per type per contact. Duplicate normalized points within the same contact are rejected; the same household may intentionally share a point without automatically merging two people.
3. **Households and person relationships.** Workspace-scoped households group contacts without changing contact identity. Labeled person relationships support spouse/partner/household member and a bounded generic relationship label. Self-links, duplicate inverse links and cross-workspace links fail closed. Household membership never becomes a dedupe key by itself.
4. **Assignment and prioritization.** Contacts can be assigned to one or more active workspace members. Assignments to revoked or other-workspace members fail. Unassign/reassign preserves activity history and records actor/time. Existing `leadType` (`Hot | Warm | Nurture`) remains the only prioritization authority; `relationship`, `intent`, `source` and `pipelineStage` semantics do not change. No independent rating is stored, imported or displayed.
5. **Richer realtor facts.** Buyer/seller details expand only for gaps already identified by the matrix: additional property types/tenure, mortgage/property facts and household/partner context. Existing price, area, beds, baths, timeline, pre-approval, lender, seller address/price/timeline/motivation remain backward compatible. Field validation is typed, bounded and documented; absent facts remain unknown rather than inferred.
6. **Typed custom fields.** A workspace owner can define/archive bounded custom-field definitions of type `text`, `number`, `date`, `boolean` or `single-select`; owner and assistant can set authorized values. Definitions have stable IDs, name, type, validation/options and display order. Type changes that would invalidate stored values are rejected or require an explicit migration preview; values are data, never executable expressions/schema/SQL.
7. **Import and intake compatibility.** Existing single phone, secondary phone and email deterministically map to contact points without changing contact IDs. Household, assignment, richer facts and custom fields import only through explicit previewed mappings. Unmapped/invalid values remain row notes/rejections or Story 3.1 incomplete records; imports never create field definitions implicitly or merge solely on household.
8. **Safe archive and restore.** Contact “delete” is archive/restore with actor, time and reason. Archived contacts disappear from default Today, Contacts, Pipeline, new Smart List evaluation and new task assignment while preserving notes, activities, tasks, mail history, import links, contact points, household relationships, assignments and custom values. Detail/history remains available to authorized users through an explicit archived view. Restore returns the same ID/history. Hard delete is absent until a separate retention policy exists.
9. **UI integration.** Contact create/edit/detail, Contacts, `/workspace` assignment selectors and Story 3.1 work surfaces expose the new facts without removing current mobile Call/Text/Email, notes or follow-up actions. Permission, conflict, archived, revoked-assignee, validation, success and persistence-failure states are explicit and accessible at desktop/390px in both themes.
10. **Workspace isolation and gates.** Every new table uses canonical `workspace_id`, workspace/member-consistent foreign keys and Story 3.0 RLS; no new tenant authority uses legacy `owner_id`. Two-workspace/revoked-member tests, migration/backfill tests, import compatibility, archive/history regression, CLI smoke, browser/accessibility QA, lint, typecheck, complete tests and production build pass.

### Normative Contract Clarifications

These clarifications refine the acceptance criteria without replacing or weakening their wording.

#### Contact points and legacy compatibility (AC 1, 2, 7, 10)

- `contact_points` is the canonical post-migration source of truth. A point has stable ID, `workspace_id`, `contact_id`, type `phone | email`, required label, display value, normalized value, primary flag, applicable consent/subscription facts, display order, created/updated timestamps and archive actor/time/reason. The initial active bound is **three phones and two emails per contact**; archived points do not count toward the bound. This adapts the independently observed three individual phone slots and two individual email slots at the pinned reference revision into Omnix's own model rather than copying its form.
- Labels use 1–80 trimmed printable characters. Control characters fail validation. Phone display values use 1–40 printable characters, must contain 7–15 digits, and reuse the current import identity rule: remove non-digits, then remove a leading US country digit only when the result is exactly 11 digits beginning with `1`. Email display values are at most 254 characters and normalize by trim plus lowercase using the current email validator. No provider-specific canonicalization, fuzzy phone matching or inferred consent is introduced.
- Within one contact, two active points with the same type and normalized value fail; there is at most one active primary per type. The same normalized point may belong to different contacts, so no workspace-wide uniqueness constraint is allowed. Restoring a point that would exceed the active bound or violate duplicate/primary invariants fails as a conflict until the caller resolves it.
- Migration backfill maps legacy `phone` to a primary phone labeled `primary`, `secondaryPhone` to a non-primary phone labeled `secondary`, and `email` to a primary email labeled `primary`. Equal normalized legacy phone values coalesce into one primary point. A count-only preflight aborts the transactional backfill if a non-empty legacy scalar cannot pass the normalization/validation contract; no scalar value is silently dropped or logged as PII.
- After backfill, legacy reads remain deterministic projections: `phone` is the active primary phone or first active phone by display order/creation/ID; `secondaryPhone` is the first remaining active phone by the same order; `email` is the active primary email or first active email. Legacy scalar writes must translate through the same contact-point application service and update the compatibility projection in the same transaction. Direct scalar and canonical writes cannot become two independent authorities.

#### Households and person relationships (AC 1, 3, 7, 10)

- A household has a stable ID and a required name of 1–80 trimmed printable characters. Household membership is workspace-local and does not imply identity, assignment, primary contact or permission.
- A person relationship uses one of `spouse | partner | household-member | other`. `other` requires a generic label of 1–80 trimmed printable characters; the fixed kinds reject a generic label so two competing labels cannot exist. The pair is stored canonically as an unordered pair of distinct contact IDs with one active relationship per pair. Self-links, reverse duplicates, cross-workspace pairs and restore operations that recreate a duplicate fail closed.
- Partner/spouse contact details remain on the linked contact's own contact points and birthday. They are not duplicated inside buyer/seller JSON. A household name or relationship never participates in import identity matching.

#### Exact richer buyer/seller facts (AC 5, 7)

- Existing buyer facts remain authoritative for price minimum/maximum, areas, beds, baths, timeline, pre-approval and lender. The sourced gaps add `mortgageType` (`conventional | fha | va | cash | unknown`), bounded desired property type text (80 characters) and current tenure (`owns | rents | unknown`). Partner context uses the relationship contract above.
- Existing seller facts remain authoritative for property address, target price, timeline and motivation. The sourced gaps add whether there is a property to sell (`yes | no | maybe | unknown`), bounded property type, basement, parking, condition and listing-status text (80 characters each), plus bedrooms and bathrooms using the existing finite non-negative numeric validation. Existing `homePurchaseDate` carries the home-anniversary fact; existing buyer/seller `timeline` carries buying/selling/planning horizon. No duplicate anniversary or timeline field is added.
- Unknown or absent richer facts stay absent/`unknown` according to their declared type. Import aliases must preview an explicit destination; an observed source field that maps to an existing Omnix fact uses that fact instead of creating a duplicate field.

#### Archived identity matching and atomic import (AC 7, 8, 10)

- Import/intake identity lookup includes active and archived contacts in the order already established by Story 1.3: provider/external ID, normalized email, then normalized phone. Exactly one archived match produces an explicit `archived-match` row outcome with no create, update, merge or automatic restore; the authorized operator must restore the same contact ID and rerun. Identity signals resolving to different contacts, or a shared phone/email resolving to more than one contact, produce `ambiguous-identity` and no mutation. Household membership never resolves the ambiguity.
- Each collapsed import target group is atomic in live and memory adapters: contact create/update, canonical contact points, richer facts, household/assignment/custom values, external link, required activity evidence and result state either all persist or all roll back for that group. Independent groups may still produce the honest partial result required by Story 1.3.
- The public contact `remove()` lifecycle becomes archive and therefore **must not** be used for import rollback. Live execution requires one transaction/RPC (or an equivalent repository transaction boundary); memory execution snapshots/restores the group. If the atomic boundary is unavailable, execution fails before the first write. A failed group cannot leave an archived zombie contact, external link, point, relationship, assignment, custom value or success activity.
- The current import alias `rating` continues to mean Hot/Warm/Nurture only when its value is accepted by the existing `leadType` allowlist. No second rating field or coercion is introduced.

### Product Decision — Single prioritization authority (resolved 2026-08-11)

The reference matrix records a rating-shaped capability, but its observed values are temperature-like and duplicate Omnix's established Hot/Warm/Nurture axis. The realtor's sourced requirements explicitly organize clients from Hot through Nurture and define follow-up cadence by those values; they do not request or define a second score.

The Product Owner therefore declines an independent rating for this release. `leadType` remains the single prioritization authority, the legacy `rating` import alias remains only an allowlisted synonym for `leadType`, and no rating schema, default, ordering, UI or import destination is created. A future independent score requires new user evidence and a separate story; it must never silently reinterpret existing data.
