## Story

**As a** realtor or authorized assistant,  
**I want** reusable Smart Lists, an inbox for incomplete incoming records, and one searchable task/activity work queue,  
**so that** every lead is organized, recoverable and actionable without relying on memory or losing imperfect intake data.

**Traceability:** C-04; D-14; D-16; L-02–L-10; P-01–P-05; A-08 (CRM activity only); B-14 foundation in `docs/prd/omnix-reference-parity-matrix.md`. This is the first executable increment in `docs/prd/omnix-crm-parity-roadmap.md`.

**Dependencies:** Stories 1.2, 1.3 and 1.5 are Done and provide validated contact commands, secure import/intake, repository seams, bounded contact search and live/demo disclosure. **Story 3.0 Shared Workspace Authority is a hard prerequisite and must be Done before implementation starts**; it supplies canonical `WorkspaceScope`, forward-only `workspace_id` backfill, owner/assistant membership, membership-derived RLS and intake binding. Story 2.2 is not a code dependency.

## Acceptance Criteria

1. **CLI-first work management.** Package scripts expose documented, non-interactive commands for Smart List create/list/show/apply/update/archive, incomplete-record list/show/convert/archive, and task/activity list/create/complete/archive. Commands use the same application services, required `WorkspaceScope` and repository interfaces as the UI, return a non-zero exit code on validation or persistence failure, never require a browser and never print contact PII unless the operator explicitly requests record details.
2. **Persisted Smart Lists.** An authorized workspace member can create, name, edit, apply and archive a Smart List. A list stores canonical `workspace_id` plus a versioned, validated filter definition rather than raw SQL/code. The initial allowlist supports the current contact fields needed by the matrix: bounded free-text query; temperature; relationship; intent; source; pipeline stage; tags; city/state/postal code; buyer price minimum/maximum; buyer/seller timeline text; and next-touch before/on/after/empty. Enum filters support equality or membership, text supports bounded contains/equality, numbers support minimum/maximum, dates support before/on/after/empty, and tags support any/all. Unknown fields/operators, more than 20 criteria, names over 80 characters and free-text over 200 characters fail closed with a field-level reason.
3. **Deterministic Smart List results.** Applying the same saved definition to the same repository state returns the same ordered contact IDs in CLI and UI. Results are workspace-scoped and membership-filtered, bounded to 500 contacts for the current client scale, preserve the established Hot → Warm → Nurture priority unless the list defines a supported explicit sort, and expose the active criteria plus a clear/reset path. Archived lists cannot be applied until restored and are not hard-deleted.
4. **Incomplete-record quarantine.** Import or authenticated intake data that cannot become a valid `Contact` but has at least one safe identity signal (name, phone, email or provider external ID) is stored as a workspace-scoped incomplete record with source, external ID when present, normalized allowlisted candidate fields, validation reasons, status (`pending`, `converted`, `archived`) and timestamps. Workspace binding comes only from Story 3.0's authenticated/intake authority, never a caller-supplied ID. Arbitrary raw request bodies, authorization headers, secrets and unmapped columns are not persisted. Payloads with no safe identity signal remain rejected and are not stored as contact PII.
5. **Review, convert and archive.** An authorized workspace member can search/refresh the incomplete inbox, inspect its safe fields and reasons, correct data, preview the same conservative duplicate/merge decision used by imports, then convert exactly once into a full contact in the same workspace. Conversion and status/link update are atomic and idempotent; repeat conversion returns the original contact result. “Remove” is implemented as archive with actor/time/reason and optional restore, not destructive deletion.
6. **Unified activities and tasks.** Omnix persists immutable CRM activity events and mutable follow-up tasks. The initial event types cover contact created/updated/imported, note added, touch recorded, incomplete record converted, and task created/completed/archived. A task has canonical workspace, optional contact, title, optional description, due date/time, status (`open`, `completed`, `archived`), creator/assignee membership identity, and timestamps. Existing note/touch/contact/import commands append the corresponding event through the application layer; no provider email/SMS/call is fabricated.
7. **Work queue operations.** CLI and `/activities` provide bounded search plus day/due-range, status and contact filters; open tasks sort overdue first, then due time, then creation time. The user can create, complete, reopen and archive one task, and bulk-complete or bulk-archive an explicit allowlisted set of task IDs. Each command is idempotent or returns a clear no-op; empty selection, cross-workspace IDs, revoked/unauthorized assignees and more than 100 IDs fail closed. Activity events remain append-only and cannot be edited or deleted through product commands.
8. **Realtor-facing review surfaces.** `/contacts` can apply/manage Smart Lists without losing current URL-backed search; `/contacts/incomplete` provides the quarantine inbox; `/activities` provides task and timeline views; contact detail shows its chronological activity/task history. Empty, loading/pending, validation, success, no-op and persistence-failure states are explicit. The existing Today, Contacts, Import, contact detail/edit, Pipeline, Insights, Omnix and Mailers routes continue to work.
9. **Workspace isolation and honest modes.** Supabase tables use canonical `workspace_id`, membership-aware foreign keys/indexes and Story 3.0 RLS to prevent cross-workspace reads/writes, including relationships between incomplete records, contacts, tasks and activity events. No new table treats legacy `owner_id` as tenant authority. The seeded in-memory adapters implement the same `WorkspaceScope` contracts for sample mode and visibly remain non-durable; there is no silent fallback after a live write fails.
10. **Quality evidence.** Unit tests cover the filter grammar/evaluator, validation limits, ordering, incomplete-record state machine, conversion idempotency, task transitions, activity immutability and redaction. Repository/route tests cover memory and Supabase mappings plus two-workspace membership isolation. CLI smoke tests prove all operations without UI. Browser QA covers desktop and 390px, light/dark, keyboard/focus, no horizontal overflow, semantic tables/lists/forms, safe bulk confirmation, explicit errors, no broken assets and no unexpected console errors. `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` pass.

## Dev Notes

### Existing contracts to preserve

- `ContactRepository` is the UI/data seam and currently exposes contact CRUD plus append-only notes. New domains should use typed repository interfaces so demo and Supabase implementations remain interchangeable. [Source: `packages/crm/lib/data/repository.ts`; `docs/architecture/tech-stack.md#data-layer-approach-for-phase-1`]
- The current query is bounded to 200 characters, searches name/phone/email/city/ZIP/tags and sorts Hot → Warm → Nurture. Smart Lists extend this behavior; they must not fork an inconsistent contact query path. [Source: `packages/crm/lib/application/contact-query.ts`; parity L-02–L-09]
- Contact validation requires at least a first or last name. Import/intake already has conservative identity merge, external links and idempotency receipts. Quarantine must attach at that validation boundary rather than weaken `Contact`. [Source: `packages/crm/lib/application/contact-commands.ts`; `packages/crm/supabase/migrations/0002_contact_import_intake.sql`; Story 1.3]
- Notes are append-only, and current touch commands update last/next touch. Activity events record those facts; they do not replace source fields or make mutable notes. [Source: `packages/crm/lib/domain/contact.ts`; `packages/crm/lib/application/contact-commands.ts`; `packages/crm/supabase/migrations/0001_init.sql`]

### Failure and security rules

- Filters are data, never executable code. Validate before persistence and again before evaluation.
- No raw request body, token, header, secret or unmapped import column enters quarantine.
- Conversion and bulk operations must be atomic, workspace-scoped and replay-safe.
- Activities are evidence. Provider communication events must wait for provider receipts in later stories.
- Archive is reversible; permanent retention/deletion policy is not invented in this story.

### Autonomous decisions

- [AUTO-DECISION] Combine three parity gaps in one first story → Yes, as one bounded vertical work-queue foundation (reason: Smart Lists determine who is in scope, quarantine prevents intake loss, and tasks/activities make the resulting records actionable; they share repository/RLS/CLI patterns but no external provider dependency).
- [AUTO-DECISION] Persist rejected raw payloads → No; persist only normalized allowlisted fields when a safe identity signal exists (reason: data minimization and secret/PII risk).
- [AUTO-DECISION] Implement reference “deleted” status as hard delete → No; use archive/restore with actor/time/reason (reason: CRM auditability and the matrix's safe-delete boundary).
- [AUTO-DECISION] Build a parallel dashboard-contact flag → No; use a system Smart List over the single contact source of truth (reason: avoids contradictory record membership).
