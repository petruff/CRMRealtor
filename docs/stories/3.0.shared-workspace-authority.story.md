## Story

**As a** realtor who authorizes an assistant,  
**I want** every Omnix record and command governed by one canonical workspace authority,  
**so that** we can collaborate on the same CRM while all other workspaces remain isolated.

**Traceability:** RQ-22 in `docs/prd/realtor-requirements-coverage.md`; delivery-order item 1 and C-07 foundation in `docs/prd/omnix-reference-parity-matrix.md`; hard architecture prerequisite for Story 3.1 and every later persistent domain.

**Dependencies:** Stories 1.1–1.5 are Done. This story must be Done before Story 3.1 writes Smart Lists, incomplete records, tasks or activity events.

## Acceptance Criteria

1. **Canonical workspace model.** A forward-only SQL migration creates `workspaces` and `workspace_members`. A workspace has an immutable ID, name and timestamps. Membership role is constrained to `owner | assistant`, membership state is explicit, a user cannot have duplicate active membership in one workspace, and database/application invariants prevent a workspace from having zero active owners. The initial product supports exactly one active owner per workspace.
2. **Forward-only tenant backfill.** The migration creates one workspace for each current distinct `owner_id`, creates the matching owner membership, and backfills non-null `workspace_id` on all current tenant-bearing CRM data: `contacts`, `notes`, `mailers`, `mailer_sends` through their parent authority, `contact_external_links` and `contact_intake_receipts`. Existing business IDs, timestamps and relationships remain unchanged. Pre/post count, null and referential assertions fail closed rather than silently orphaning rows. Legacy `owner_id` columns may remain during a compatibility window but are not the tenant authority for new application writes.
3. **Required `WorkspaceScope`.** `RepositoryContext` exposes a non-optional typed `WorkspaceScope` containing authenticated user ID, active membership ID, workspace ID and role. Live repositories and application commands receive or close over this scope; routes/actions/queries never authorize using caller-supplied `owner_id` or `workspace_id`. Seed/sample mode has an explicit sample `WorkspaceScope`, uses the same repository contracts and remains visibly non-durable.
4. **Membership-derived RLS.** RLS for every backfilled table derives access from the caller's active `workspace_members` row. Owner and assistant can read/write ordinary CRM records in their workspace. Assistant cannot manage workspace authority/membership, ownership, connector/API secrets or protected settings. Composite constraints or equivalent database checks reject cross-workspace relationships where supported; isolation is not only a UI/query filter.
5. **Two-tenant proof.** Automated SQL/repository tests create Workspaces A/B, Owners A/B, Assistant A and a revoked Assistant A. Tests prove Owner A and Assistant A share intended rows; Owner B cannot read/write/link A; A cannot read/write/link B; revoked membership loses access; spoofed workspace/owner values fail; and cross-workspace notes, mailer sends and external links cannot be created. Product commands cannot turn service-role capability into arbitrary tenant access.
6. **Intake workspace binding and compatibility alias.** Authenticated automatic intake resolves one server-configured workspace binding; the request cannot select a workspace/owner. Existing `CRM_INTAKE_OWNER_ID` remains a documented temporary compatibility alias that resolves the owner's unique active workspace and fails closed when missing, ambiguous, revoked or mismatched. A canonical `CRM_INTAKE_WORKSPACE_ID` binding takes precedence when both are present; contradictory bindings fail with no write. External links and idempotency receipts always use the resolved workspace, and service-role/token values remain server-only.
7. **CLI-first administration and health.** Before any workspace management UI, CLI commands bootstrap/show a workspace, list/add/revoke membership with role enforcement, and run workspace health. Health reports migration/backfill completeness, authenticated membership/workspace binding, RLS-safe repository access and intake-binding status without dumping PII, tokens, service keys or rows from other workspaces. Commands provide stable documented exit codes and machine-readable output.
8. **Authenticated health API and auditability.** An authenticated owner-only workspace health endpoint returns the same redacted checks for the current workspace. If a public process/readiness response is introduced, it contains no tenant/account counts, environment values or customer data. Structured audit events capture membership/authority changes with actor, workspace, action, result, timestamp and correlation ID while retaining historical actor identity after revocation.
9. **Compatibility and gates.** Today, Contacts, Import/Intake, contact detail/edit, Mailers, Pipeline, Insights, Omnix and sample mode continue through the new context. Migration verification, repository/RLS tests, intake alias/binding negative tests, CLI/API health smoke, lint, typecheck, complete tests and production build all pass. Browser smoke with separate accounts proves no cross-workspace leak and truthful sample/live state.

## Out of Scope

- Smart Lists, incomplete records, tasks or activities (Story 3.1); rich contact/household fields and archive lifecycle (Story 3.2); connectors or AI.
- Roles beyond `owner | assistant`, multiple owners, ownership transfer, public client access, billing/team hierarchy or email invitation delivery.
- Dropping legacy `owner_id` in this migration, destructive rollback, production deployment or declaring real-account UAT complete.

## Dev Notes

### Current contracts and required change

- Current SQL and repositories authorize by `owner_id`; adding new owner-bound tables first would preserve the wrong single-user tenant model. Story 3.0 establishes `workspace_id` as the sole authority for future persistence. [Source: `packages/crm/supabase/migrations/0001_init.sql`; `0002_contact_import_intake.sql`; `packages/crm/lib/data/index.ts`; @architect gate]
- `RepositoryContext` currently contains repositories plus `isLive`/email but no tenant object. Add required `WorkspaceScope`; do not add optional workspace parameters to individual queries. [Source: `packages/crm/lib/data/index.ts`]
- Current automated intake constructs a privileged repository with a configured owner and a service-role client. Replace the product-command authority with a verified server-side workspace binding; keep the client private to intake. [Source: `packages/crm/lib/data/automation-context.ts`; Story 1.3]
- Existing IDs and history are customer records. The forward-only migration must assert completeness before authority shifts. [Source: current migrations; `.aexos-core/constitution.md#v-quality-first-must`]
- Supabase/Postgres/Auth, typed repositories and equivalent memory/live contracts remain the approved stack. [Source: `docs/architecture/tech-stack.md#decision`; `#data-layer-approach-for-phase-1`]
- CLI must be operational before UI. [Source: `.aexos-core/constitution.md#i-cli-first-non-negotiable`]
