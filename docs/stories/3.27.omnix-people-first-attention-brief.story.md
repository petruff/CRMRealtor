## Story

**As Judith,**

**I want** “Who needs attention?” to identify the actual people, explain why each one matters and show the most important next actions first,

**so that** I can run follow-up from a concise decision brief instead of opening a long list of anonymous system records.

**Traceability:** Explicit user report received 2026-08-23; Story 3.6 AC2, AC5, AC6 and AC9; Story 3.11 progressive-disclosure precedent; Story 3.12 alert presentation precedent.

**Dependencies:** Story 3.6 remains the authority for deterministic ordering, record-level citations, safe links, workspace scope, read-only behavior and the stable `omnix-copilot.v1` response. This story is an additive presentation refinement and does not activate Story 5.1 generative or outbound scope.

## Acceptance Criteria

1. **The answer is people-first, not rule-first.** For contact-backed alerts, every visible row leads with the contact's display name. Raw rule identifiers such as `overdue-follow-up`, `due-today-follow-up` and `upcoming-follow-up` are never used as customer-facing labels.
2. **Judith receives a concise operational summary.** The response states the total number needing attention and the deterministic distribution across overdue, due today and upcoming work. Empty states explain that no follow-up needs attention instead of showing an internal catalog message.
3. **Useful CRM context is visible before navigation.** Each contact row includes a human-readable timing/reason plus available operational context from authorized CRM facts, limited to lead type, relationship/pipeline stage and source. Missing facts are omitted rather than replaced with internal IDs or placeholders.
4. **The fixed alert order remains authoritative.** Items retain the deterministic catalog order and priority produced by Story 3.6. Presentation may group adjacent alerts by action horizon, but it may not re-score, invent urgency, use a model or mutate CRM data.
5. **Large results use progressive disclosure.** The assistant renders no more than six attention items initially. A clearly named control reveals the next six without losing keyboard position; a separate link to `/alerts` remains available for the complete operational queue. All results remain reachable.
6. **Actions name their destination.** Contact-backed items use a clear action such as `Open [contact name]`; task-backed items use the task title and a truthful task/activity destination. Generic `Review source` is not the primary row action.
7. **Evidence is recognizable.** Inline evidence links use the related contact or task label when it can be resolved from the authorized response. The UI does not show `Contact record 1`, rule slugs, UUIDs or raw fact keys as the main user-facing explanation. The canonical citations and source facts remain intact and inspectable.
8. **No alert is duplicated in the same answer.** Alerts represented in the people-first answer are not rendered again in a second raw-alert list. Multiple alerts for one record may remain distinct when they represent distinct fixed-catalog rules, but each row must identify the person/task and reason clearly.
9. **The assistant remains accessible and responsive.** The compact launcher and full `/omnix` surface work at 390, 768 and 1440 pixels with no horizontal overflow, obscured controls or pointer-only interaction. Lists, headings, live status, focus order and expansion controls are screen-reader coherent; reduced motion preserves all meaning.
10. **Contracts and gates prove the refinement.** Focused tests cover real contact names/context, summary counts, fixed order, six-item batching, named actions, recognizable evidence, empty state and no duplicate raw rendering. `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` pass from `packages/crm`; @qa records an independent verdict before release handoff.

## Dev Notes

### Existing implementation seams

- `packages/crm/lib/application/omnix-copilot-service.ts` currently maps each alert directly to an answer item with `label: alert.rule`; this is the source of the visible rule slugs. The service already holds the authorized contact and task snapshots required to project human labels.
- `packages/crm/components/omnix-copilot.tsx` currently renders every answer item in one unbounded list and uses `Review source` plus numbered entity labels. Progressive disclosure belongs in this shared result component so the launcher and `/omnix` remain coherent.
- `packages/crm/components/omnix-copilot-view-model.ts` is the presentation boundary for resolving answer/citation labels. Prefer additive view-only metadata over expanding the canonical citation contract.
- `packages/crm/lib/domain/omnix-copilot.ts` and existing CLI JSON remain compatibility authorities. The canonical alert `rule`, `priority`, `order`, `recordId`, `href` and citations remain unchanged.
- The architecture requires a deterministic read-only alert evaluator, UI as a projection of application services, responsive accessibility gates and no invented business metrics.
