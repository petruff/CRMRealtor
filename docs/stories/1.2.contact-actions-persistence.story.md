## Story

**As a** solo real estate agent,  
**I want** to create and maintain contacts, append notes, and record completed follow-ups from the CRM,  
**so that** the triage view reflects my real work instead of remaining a read-only demonstration.

**Traceability:** Phase 1 requires contacts, first-class timestamped notes, automatically scheduled follow-ups that remain manually adjustable, pipeline stages, and fast mobile entry. [Source: `docs/prd/requirements-analysis-v2.md#phase-1--the-thing-shes-missing-today-target-weeks`; `docs/prd/requirements-analysis-v2.md#41-she-said-yes-to-gmail-d--but-it-does-not-fit-her-lead-sources-`]

**Dependency:** Story 1.1 is Done and provides the contact model, cadence engine, repository boundary, Supabase implementation, seeded memory implementation, and Apple-inspired responsive design system.

## Acceptance Criteria

1. **Create a contact.** From the Contacts screen, the user can open a mobile-first form and create a contact with at least a first or last name. The form exposes the existing contact model without renaming its Hot / Warm / Nurture, relationship, intent, source, or pipeline values. A successful create returns the user to the new contact detail page.
2. **Fast entry with progressive detail.** Name, primary phone, email, and lead type appear first; secondary contact details, address, dates, CRM classification, buyer/seller criteria, referral, tags, and subscription state remain available in clearly grouped optional sections. Existing 44×44px targets, focus visibility, AA contrast, reduced-motion behavior, light/dark themes, and 390px responsiveness are preserved.
3. **Edit a contact.** The contact detail page exposes an Edit action. Saving changes updates the existing record without changing its `id` or `createdAt`, and redirects back to the same detail page with the updated values visible.
4. **Manually adjust follow-up.** Create/edit accepts a valid `nextTouchAt` date. A user-supplied date sets `touchDateOverridden`; otherwise a new active contact receives the existing cadence engine's computed next touch. Closed and lost contacts remain dormant.
5. **Append a note.** Contact detail accepts a non-blank note, saves it through `ContactRepository.addNote`, and displays it newest-first with its timestamp. Notes are append-only; this story adds no edit or delete control.
6. **Record a completed touch.** Contact detail includes a thumb-reachable action that applies the existing `recordTouch()` command, persists `lastContactedAt`, computes the next touch, clears a spent manual override, and moves a `new` contact to `contacted`.
7. **Honest and safe mutation behavior.** Mutations use the existing repository selected by `getRepository()`: Supabase when configured and authenticated, seeded memory mode otherwise. Inputs are normalized and validated on the server; invalid or failed writes show a useful message and never claim success.
8. **UI-independent command layer.** Create, update, add-note, and record-touch rules live outside React components so they can be unit-tested and invoked independently of the UI, following the project's CLI-first hierarchy.
9. **Regression protection.** Existing cadence and triage behavior stays green. Focused tests cover successful commands, invalid names/notes/dates, automatic and manual cadence behavior, immutable identity fields, and repository failures. Project lint, typecheck, tests, and production build pass.

## Out of Scope

- Spreadsheet, phone, Boldtrail, or Mailchimp import.

- Provisioning Supabase or Google OAuth credentials.
- Mailchimp, Gmail, Calendar, SMS, or website integrations.
- Assistant roles and permission enforcement.
- Automated visual-regression/axe infrastructure beyond focused runtime accessibility review.

### Data and Command Boundaries

- `ContactRepository` already exposes `create`, `update`, `notesFor`, and `addNote`; both memory and Supabase implementations exist. UI code must continue to depend on this interface. [Source: `docs/architecture/tech-stack.md#data-layer-approach-for-phase-1`]
- `recordTouch`, `overrideNextTouch`, and `ensureNextTouch` already encode cadence behavior. Call them; do not reimplement intervals in UI or server actions.
- Contact and note schema is defined in `packages/crm/lib/domain/contact.ts` and mirrored in `packages/crm/supabase/migrations/0001_init.sql`. Notes are append-only and the database requires trimmed non-empty content.
- The schema accepts a contact when either first or last name is present. Persisted identity and creation timestamps are repository-owned.

### Architecture and File Locations

- Next.js 15 App Router and server components are the approved stack; route handlers/server mutations belong inside `packages/crm/app`, shared UI inside `packages/crm/components`, domain rules inside `packages/crm/lib/domain`, and repository-independent application commands inside `packages/crm/lib`. [Source: `docs/architecture/tech-stack.md#decision`; `docs/architecture/tech-stack.md#source-tree`]
- No component library, state manager, ORM, or new external dependency is authorized for this story. [Source: `docs/architecture/tech-stack.md#decision`]
- Server components and URL/server state are preferred; introduce client components only where pending/error form feedback requires them. [Source: `docs/architecture/tech-stack.md#decision`]

### Security and Error Handling

- All mutation input must be treated as untrusted even when native HTML constraints exist.
- Supabase ownership and RLS remain the persistence boundary; no service-role key or client-side database mutation is allowed.
- Failure must remain explicit. Do not silently fall back from a failed live Supabase write to memory mode.

### Testing

- Use the existing Vitest setup in `packages/crm` and keep pure command tests adjacent to the command module.
- Required scenarios: at-least-one-name validation, optional value normalization, invalid enum/date rejection, automatic cadence on create, manual override, immutable identity on update, non-blank append-only note, `recordTouch` behavior, and repository error propagation.
- Runtime review must cover create → detail, edit → detail, append note, and record touch at 390px and desktop.

### Project Structure Notes

- The configured sharded architecture files for coding standards, source tree, frontend architecture, testing strategy, and database schema are absent. This story uses the existing `docs/architecture/tech-stack.md`, domain types, migration, completed Story 1.1, and live source tree as the available sources of truth.
