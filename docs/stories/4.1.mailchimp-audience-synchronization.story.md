## Story

**As a** workspace owner,  
**I want** Omnix connected to one explicitly selected Mailchimp audience,  
**so that** contact temperature tags flow out and signups/unsubscribes flow back without duplicate contacts, feedback loops or false success.

**Traceability:** RQ-11–RQ-14 in `docs/prd/realtor-requirements-coverage.md`; the Mailchimp row in `docs/prd/omnix-crm-parity-roadmap.md`; Story 3.5 connector contracts.

**Dependencies:** Story 3.5 supplies connection OAuth, encrypted secrets, durable jobs, approvals, signed-webhook ingress, reconciliation, receipts and disconnect. Story 3.2 supplies canonical email contact points and subscription facts; this story does not create a temporary competing email authority. Stories 3.0/3.1 supply workspace authority and incomplete-record/activity evidence.

## Acceptance Criteria

1. **CLI-first connection and audience authority.** Documented CLI commands initiate/complete Mailchimp OAuth, list redacted remote account identity and available audiences, select exactly one audience, inspect health/scope-equivalent authorization, preview synchronization, run a bounded page, reconcile and disconnect. UI invokes the same application services only after CLI proof. The owner alone authorizes, selects/replaces the audience or disconnects; an assistant can see policy-allowed redacted health but never tokens.
2. **Exact workspace/account binding.** The connection persists workspace, Mailchimp account/data-center identity and selected audience ID/name as redacted Story 3.5 metadata; encrypted access token and endpoint material remain server-only. Every job/webhook/cursor binds the connection and selected audience. Caller input cannot choose a workspace, data center, API base or different audience. Re-selecting an audience requires owner confirmation, a new baseline preview and invalidates no CRM history.
3. **Deterministic source-of-truth and tag mapping.** Omnix is authoritative for Hot/Warm/Nurture (`leadType`) and sends only a versioned, owner-approved mapping of those three values to Mailchimp tags. Mailchimp is authoritative for its audience membership/subscription events; an unsubscribe immediately makes the canonical email point not emailable for this channel. Other Mailchimp tags, merge fields and campaigns are preserved and never silently overwritten. An unsubscribe cannot be reversed by ordinary tag reconciliation; resubscription requires fresh provider-valid consent and an explicit governed operation.
4. **Idempotent outbound synchronization.** A tag/member change is a versioned Story 3.5 action intent and durable job keyed by workspace, connection, audience, canonical normalized email/subscriber hash, mapping version and desired operation. Approval/enqueue occurs once. Retries, restarts, overlapping drains and duplicate contact-change events cannot add/remove the same tag twice or report success without a Mailchimp/reconciliation receipt. Bulk backfill requires a count-only preview, bounded resumable batches and owner approval of the exact snapshot/mapping version.
5. **Inbound signup, update and unsubscribe identity.** Verified selected-audience events normalize through the existing intake contract. Exactly one canonical normalized-email match updates the same contact/subscription fact and appends activity evidence. No match creates a contact only through Story 1.3's validated idempotent intake when minimum fields are valid; otherwise it creates a Story 3.1 incomplete-record review item. Multiple/archived/conflicting matches create an explicit review outcome with no merge, restore or mutation. Provider member/audience identity is stored as an external link and never inferred from a display name.
6. **Loop prevention and conflict handling.** Every mutation carries origin, connection, provider member identity, source event/job and correlation. Inbound application compares current canonical state before writing; the resulting local activity cannot enqueue an equivalent outbound change. Outbound receipts/cursors suppress echo without suppressing a later genuine provider event. Concurrent tag/subscription changes resolve under AC3; ambiguous order enters reconciliation instead of last-write-wins guessing.
7. **Webhook and replay safety.** Mailchimp webhook requests are verified over bounded raw input using the Story 3.5 configured verifier before parsing or mutation, bound through an opaque connection endpoint and deduplicated by delivery/body evidence. Duplicate, stale, invalid, wrong-audience and out-of-order deliveries cause no second business mutation. Accepted delivery persists redacted receipt metadata and queues processing before a prompt success response; raw bodies, emails and signatures do not enter operational logs/receipts.
8. **Reconciliation and recovery.** Initial and periodic reconciliation page the selected audience in bounded resumable batches, persist private cursor/checkpoint state, respect rate limits and compare provider membership/tags/subscription with canonical CRM facts. Missing webhooks, expired checkpoints, 429/5xx, revoked authorization and partial batches are visible and recoverable. Drift repair follows AC3, records per-item outcomes and never turns a provider unsubscribe into an automatic CRM-driven resubscribe.
9. **Receipts, disconnect and retained history.** OAuth, audience selection, probe, each outbound attempt, webhook acceptance/rejection, reconciliation and revocation have redacted append-only Story 3.5 receipts. Disconnect blocks new work, attempts provider revocation where supported, cryptoshreds local token material and reports confirmed versus unconfirmed revocation honestly. Contact, subscription and activity history remains, but no disconnected credential, cursor or webhook can mutate it.
10. **Truthful UX and release evidence.** `/connections` shows the exact account/audience, health, last reconciliation, mapping version and `disabled | authorizing | active | degraded | reauthorization required | disconnected` truth. It never calls CSV import or a deterministic adapter a live sync. Tests cover two workspaces/roles, OAuth replay/account swap, selected-audience isolation, tag mapping, signup/unsubscribe matching, loop prevention, duplicate webhooks/jobs, reconciliation, revocation and redaction. CLI smoke, database tests, desktop/390px accessibility, lint, typecheck, full tests and build pass; real-audience UAT proves connect → select → one tag update → verified unsubscribe → reconcile → disconnect before any live claim.

### Provider contract and configuration

- Deployment configuration keeps Mailchimp disabled by default and names `MAILCHIMP_CLIENT_ID`, `MAILCHIMP_CLIENT_SECRET`, fixed OAuth endpoints, a per-connection encrypted signing-secret authority, data-center allowlist, `audience.sync` and `audience.reconcile`. Secrets never appear in YAML. [Source: `docs/architecture/config/connector-platform.example.yaml#providers.mailchimp`]
- Official Mailchimp guidance uses OAuth 2 for third-party integrations, obtains the server prefix from OAuth metadata, supports CRM-to-audience tags, and uses audience webhooks for subscribe/unsubscribe synchronization. Access tokens remain valid until revoked, so probe/disconnect are mandatory. [Official OAuth](https://mailchimp.com/developer/marketing/guides/access-user-data-oauth-2/) · [Official tags](https://mailchimp.com/developer/marketing/guides/organize-contacts-with-tags/) · [Official webhooks](https://mailchimp.com/developer/marketing/guides/sync-audience-data-webhooks/)
- `docs/accumulated-context.md` is absent. Coherence uses the roadmap fallback, Stories 1.3/3.0/3.1/3.2/3.5, PO validation and approved connector architecture.

Likely areas are one forward migration, provider adapter/application/repository modules and tests, CLI scripts/docs, protected webhook/callback routes and additive connections/contact UI.
