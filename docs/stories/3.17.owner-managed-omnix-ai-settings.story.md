# Story 3.17 — Owner-managed Omnix AI Settings

**Epic:** 3 — CRM operating foundation  
**Status:** InReview  
**Owner:** @dev (Vulcan)  
**Quality Gate:** @qa (Argus)  
**Created:** 2026-08-14

## Story

**As the workspace owner,**  
**I want** a secure Settings screen where I can configure the Gemini API used by Omnix,  
**so that** conversational routing can be activated without editing source files or exposing credentials.

## Acceptance Criteria

1. An authenticated `/settings` route and desktop/mobile navigation affordance are available without removing existing routes.
2. Only an active workspace owner can save, rotate, enable/disable or remove a Gemini key; assistants receive a truthful read-only state.
3. The key input is a password control, never prefilled or returned after submission, and no action state, URL, log or public row contains plaintext.
4. Before persistence, the server validates the key against the selected allowlisted Gemini model using a bounded non-PII request.
5. The key is envelope-encrypted server-side with the configured KEK and workspace/version-bound AAD, then stored only in a private Supabase table.
6. A public forced-RLS projection stores only provider, model, enabled state, key fingerprint/version and audit timestamps.
7. Rotation uses optimistic version checking; removal cryptoshreds the private envelope and disables the configuration.
8. Omnix natural-language routing prefers the active workspace credential and retains the paid-private, one-query, timeout and deterministic fallback boundaries from Story 3.16.
9. Missing migration, Supabase, service-role or KEK configuration fails closed with actionable sanitized UI copy.
10. Focused security/action/UI tests, lint, typecheck, full tests and optimized build pass; no real credential is committed.
